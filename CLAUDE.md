# QuickSnap

Menu bar screenshot utility for macOS (area / window / full screen), inspired by CleanShot X. Captures via ScreenCaptureKit, auto-saves to `~/Documents/QuickSnap`, and copies to the clipboard.

## Project structure

```
QuickSnap/
  QuickSnapApp.swift     — app entry point (MenuBarExtra scene)
  Views/                 — UI only: NSWindow/NSPanel/NSView/SwiftUI View subclasses
    Overlay/               (Area/Window selection overlay)
    Preview/               (post-capture PIP thumbnail)
    Annotation/            (screenshot editor window — PaperKit markup canvas + custom toolbar)
    Settings/              (Settings window — sidebar + per-section detail views)
  Coordinators/           — owns state and window/panel lifecycles; wires Views to Services
  Services/               — stateless operations: ScreenCaptureKit calls, file I/O, permissions
```

Each feature area (capture overlay, preview thumbnail, ...) gets its own subfolder under `Views/` if it has more than one file. `Coordinators/` and `Services/` stay flat unless one grows enough files to warrant grouping.

### Layering rules — follow these for new work

1. **Views own no business logic.** An `NSView`/`NSWindow`/`NSPanel`/SwiftUI `View` may track its own transient UI state (e.g. a drag rect, a hover highlight) but reports results outward via a delegate protocol or closure. It never calls a Service directly, never knows about `ScreenCaptureKit`, file paths, etc.
2. **Coordinators own lifecycles and state.** They create/show/dismiss windows and panels, hold the delegate/closure callbacks from Views, call into Services, and decide what happens next (open a file, show an alert, chain into another capture step). A Coordinator can own multiple related Views (e.g. `CaptureCoordinator` owns one `SelectionOverlayWindow` per screen).
3. **Services are stateless and UI-agnostic.** They take plain inputs and return values or throw — no window/view references, no stored mutable state beyond simple caches. This is what makes them independently reasoned-about and, eventually, testable.
4. **One primary type per file, file name matches the type.** Small tightly-coupled support types (an error enum, a small struct only used by one file) can stay in that same file rather than being split out — don't fragment for its own sake.
5. Adding a new capture mode or feature: put its view(s) in a new `Views/<Feature>/` folder, its orchestration in `Coordinators/`, and any new primitive operations in `Services/`. Thanks to Xcode's synchronized file groups (see below), no project file editing is needed — just create the file in the right folder.

## Architecture

- `QuickSnapApp.swift` — `MenuBarExtra` entry point (menu-only, no window). Owns a single `CaptureCoordinator` as `@StateObject`.
- `Coordinators/CaptureCoordinator.swift` — orchestrates capture: permission checks, opening/closing the per-screen overlay windows, running the actual capture, then the after-capture actions per `AppSettings` (save / copy / show preview, each individually toggleable), and error alerts. Overlay sessions carry a `SelectionSessionKind` (`area` / `window` / `textRecognition`): OCR reuses the area overlay but routes the rect to `recognizeTextInArea` — Vision OCR → text to clipboard → toast — with no save/preview (the after-screenshot toggles deliberately don't apply). When Save is off, no file is written and a nil `fileURL` flows through the preview and annotation layers: the preview hides Reveal in Finder and backs drag-out with a temp PNG instead; the annotation window falls back to timestamped naming.
- `Coordinators/HotkeyCoordinator.swift` — owns the global hotkey registrations (Carbon `RegisterEventHotKey`) and re-applies them whenever UserDefaults changes (diffed against the last-applied set, since that notification fires on every defaults write). Dispatches through an `onAction` closure wired by `CaptureCoordinator`, which also calls `AppSettings.registerDefaultHotkeys()` at init.
- `Coordinators/ToastController.swift` — transient confirmation pill (centered at the top or bottom edge per `AppSettings.notificationPosition`, non-activating, click-through, auto-dismiss ~2s). Takes an optional `detail` line — the OCR flow passes the copied text (two-line truncation in `ToastView`), gated by the `showTextPreviewInToast` setting. Reuse it for any future "did the thing" feedback.
- `Coordinators/ScreenshotPreviewController.swift` — owns the floating post-capture thumbnail panel's lifecycle: show, animate in/out, auto-dismiss timer (cancelled on drag/resize/any action button press), and wires the panel's action closures (open in Finder, copy, edit) to Services. `show(...)` takes an `onEdit` closure from its caller rather than knowing what "Edit" does itself.
- `Coordinators/AnnotationCoordinator.swift` — opens/owns annotation windows (one per screenshot being viewed/edited, not a singleton like the preview panel). Toggles `NSApp.activationPolicy` between `.accessory` and `.regular` while any annotation window is open. Wires the annotation window's output actions: Copy → `ScreenshotSaver.copyToClipboard`, Save → `ScreenshotSaver.save` into the configured folder + toast confirmation (owns its own `ToastController`), Save As… → `NSSavePanel` sheet + `ScreenshotSaver.writePNG`. The original screenshot file is never overwritten. Also reads the Markup settings defaults (`AppSettings.markupDefaultColor`/`markupDefaultStrokeStep`) and passes them into `AnnotationView` — `MarkupCanvasController` deliberately never reads Services itself.
- `Services/ScreenCaptureManager.swift` — thin wrapper over ScreenCaptureKit (`SCScreenshotManager.captureImage`, a one-shot API — there is no live `SCStream`). Also holds the Screen Recording (TCC) permission helpers (`ScreenRecordingPermission`). Window captures set `ignoreShadowsSingleWindow` + `shouldBeOpaque = false` so the bare window comes back with rounded-corner alpha and no baked system shadow — `WindowBackgroundRenderer` owns presentation.
- `Coordinators/UploadCoordinator.swift` — owns the whole upload lifetime (PNG encode off-main → `UploadDestination.upload`) and all its user feedback, for **any** provider. Every upload path goes through here: automatic post-capture, the preview panel's button, and the markup toolbar's button. Progress is an `autoDismisses: false` toast replaced by a result toast; concurrent uploads are reference counted (`activeUploads`) so only the last to finish reports. Full reference in `docs/uploading.md`.
- `Services/UploadDestination.swift` — the provider protocol (`providerName` + `upload`) plus `UploadRequest`/`UploadOutcome` and the `UploadProvider` enum. Adding a provider = a conformer, an enum case, a settings section, and a branch in `AppSettings.uploadDestination`; nothing in the coordinator or the capture/preview/markup wiring changes, since they only hold an `any UploadDestination`.
- `Services/ImmichDestination.swift` / `Services/S3Destination.swift` — the two conformers. Immich orchestrates upload → album → shared link over `ImmichClient`; S3 is a single signed `PUT` against any S3-compatible endpoint (R2/B2/MinIO/Wasabi/Spaces/AWS), path-style or virtual-hosted, with S3 XML error codes translated to plain language.
- `Services/ImmichClient.swift` — stateless REST wrapper (Immich OpenAPI `3.1.0`, `/api` base, `x-api-key`): test connection, list/create albums, multipart upload, add-to-album, create shared link. Also owns `normalizedServerURL`, which tolerates a trailing `/`, a trailing `/api`, and a missing scheme (`http` for LAN addresses, `https` otherwise).
- `Services/AWSSignatureV4.swift` — hand-rolled SigV4 on CryptoKit (no SDK). **Verified against AWS's official test-suite vectors via a validated Python reference — re-run that rather than eyeballing changes; the procedure and the three bugs it caught are in `docs/uploading.md`.** Watch three things in particular: the canonical URI comes from `URLComponents.percentEncodedPath` because `URL.path` silently drops a trailing slash; the signed Host header must include a non-default port (`URL.host` omits it); and `uriEncode` is written by hand because `addingPercentEncoding` doesn't follow AWS's unreserved set or uppercase hex.
- `Services/KeychainStore.swift` — generic-password wrapper. Secrets (the Immich API key, the S3 secret access key) live here, never in UserDefaults; `AppSettings` joins them with the stored non-secret config.
- `Services/ScreenshotSaver.swift` — encode (`imageData`, the one encoder shared by disk writes, drag-out files and uploads), write to the configured save folder (`save`) or a specific URL (`write`), temp files, clipboard copy. Names come from `FilenameTemplate`; collisions get a numeric suffix; every file written is tagged via `FileTag`. `saveDirectory` delegates to `AppSettings.saveFolder`.
- `Services/FilenameTemplate.swift` / `Services/ImageFormat.swift` — token-based naming (`{date}`, `{app}`, `{window}`, `{counter}`…) and the PNG/JPEG/HEIC enum. The default template reproduces the original hardcoded convention byte for byte. Full reference in `docs/files-and-retention.md`.
- `Services/FileTag.swift` / `Services/SaveFolderCleaner.swift` — the retention pair. Every file QuickSnap writes gets an extended attribute, and the cleaner only ever deletes files carrying it (to the Trash, non-recursively). This is what makes "delete captures after N days" safe in a user-chosen folder on an unsandboxed app — **don't replace the xattr check with filename matching**, which was considered and rejected as fragile.
- `Services/LoginItem.swift` — `SMAppService.mainApp` wrapper. Registration state lives with the system, not UserDefaults, so `isEnabled` re-reads `status` every time (the user can revoke it in System Settings).
- `Services/AppSettings.swift` — UserDefaults-backed settings: custom save folder path (falls back to `~/Documents/QuickSnap` when unset or the folder no longer exists), the three after-screenshot toggles (show preview / copy / save, all default true), the window background options (`WindowBackgroundStyle` enum, padding in points, solid color stored as `#RRGGBB` via the `NSColor` hex extension in the same file), `NotificationPosition` (which screen edge the preview panel and toast appear from, default bottom), per-panel auto-dismiss durations (preview 4.5s / toast 2.2s defaults, read at schedule time so changes apply to the next timer; the preview slider's max — `previewAutoDismissNeverThreshold` — means "Never": `previewAutoDismissSeconds` returns nil and no dismiss is scheduled), the OCR toast text-preview toggle, and the Markup settings (default color hex, default stroke step 0…`markupStrokeStepCount`-1, and the four toolbar output-button visibility flags). `Keys`/`Defaults` constants are shared with the `@AppStorage` properties in the settings views (and `MarkupToolbar`'s visibility flags) — keep both in sync.
- `Services/HotkeyShortcut.swift` — `HotkeyAction` (the four actions, with default shortcuts ⌘⇧7/8/9 for area/window/full screen and ⌘⇧0 for OCR) and `HotkeyShortcut` (keyCode + modifier flags + human-readable key label, captured from an `NSEvent` at record time because deriving a label from a keyCode needs the live keyboard layout). Handles Carbon modifier conversion, the ⌃⌥⇧⌘ display string, and JSON persistence where empty `Data` means "explicitly cleared" vs. an absent key meaning "use the default" (defaults are *registered*, not written — see `AppSettings.registerDefaultHotkeys`).
- `Services/TextRecognizer.swift` — on-device OCR via Vision's modern Swift API (`RecognizeTextRequest`, accurate + language correction + auto language detection). Returns recognized lines joined with newlines.
- `Services/WindowBackgroundRenderer.swift` — composites a Window-mode capture per `WindowBackgroundStyle`: pads the window out, draws a soft shadow shaped by the window's own rounded-corner alpha, and fills the background with wallpaper (aspect-fill of `NSWorkspace.desktopImageURL`, falling back to the solid color if it can't load) / solid color / nothing (transparent). `.trimShadow` returns the capture untouched. All rendering is in the capture's pixel space — padding is converted from points via the screen's backing scale by the caller.
- `Views/Annotation/AnnotationView.swift` — SwiftUI content hosted via `NSHostingView` in the annotation window: the markup canvas on a small material mat, plus the custom toolbar pill. Owns the `MarkupCanvasController` as `@StateObject`; hands flattened exports outward via `onCopy`/`onSaveAs` closures (wired by `AnnotationCoordinator`).
- `Views/Annotation/MarkupCanvasView.swift` — `NSViewControllerRepresentable` hosting PaperKit's `PaperMarkupViewController` (the PencilKit-backed markup canvas) with the screenshot as its `contentView` background. Fit is the zoom floor (`zoomRange` = fit…fit×8): pinch/scroll zoom and pan happen natively inside the remote canvas (gesture-only — no toolbar zoom UI, deliberately). Its `Coordinator` preserves the relative zoom across window resizes via verify-and-retry enforcement — see the zoom-enforcement bullet under Non-obvious things.
- `Probe/ZoomResizeProbe.swift` — env-gated diagnostic harness for the annotation viewport (see the zoom-enforcement bullet under Non-obvious things). Inert in normal runs.
- `Views/Annotation/MarkupCanvasController.swift` — `ObservableObject` shared between toolbar and canvas: tool/color/width state applied as `PKTool`s, shape/line/text insertion via `PaperMarkup` mutation, crop (`applyCrop`), the published `visibleCanvasFrame` viewport (see the crop and zoom bullets under Non-obvious things), and async flatten-export (`PaperMarkup.draw` over the original `CGImage` at full pixel resolution). UI-layer only — never touches Services.
- `Views/Annotation/MarkupToolbar.swift` — bespoke SwiftUI pill: select/pen/highlighter/eraser, insert button (rectangle/ellipse/line/arrow/text), crop toggle, color + stroke width, and the output buttons (Copy / Save / Save As… / drag-out-file — which of them show is configured in Settings → Markup, read live via `@AppStorage` so open windows follow changes). The drag handle's payload is `AnnotatedFileDrag` (in `AnnotationView.swift`): a `Transferable` whose `FileRepresentation` flattens the canvas and writes a temp PNG lazily, only when a drop destination requests the file — there is no file on disk before that. Clicking the insert button, the color swatch, or the stroke-width squiggle (`scribble.variable`, weight-mapped to the current width) slides the pill's controls out for a preset row (colors with the system `ColorPicker` as the last option; the five widths from `MarkupCanvasController.strokeWidthPresets`; or the shape/line/text icons). Picking a color or stroke slides the main controls back; the shape row deliberately stays open for repeat insertions (the armed shape is accent-highlighted, clicking it again disarms) and dismisses only via its ✕.
- `Views/Annotation/CropOverlay.swift` — the crop surface mounted over the canvas while `MarkupCanvasController.isCropActive`: drag to create the rect, 8 handles to resize, drag inside to move, dim outside (even-odd path fill), ✓/✕ confirm bar with live pixel dimensions, Return applies / Esc cancels. Same render-pixels-to-capture-input requirement as `ShapeInsertionOverlay`.
- `Views/Overlay/SelectionOverlayWindow.swift` / `SelectionOverlayView.swift` — the full-screen borderless overlay used for both Area (drag-to-select) and Window (hover-to-highlight) modes. One overlay window is created per `NSScreen` and shown simultaneously; only the screen the user interacts with produces a result, the rest are dismissed.
- `Views/Preview/ScreenshotPreviewPanel.swift` — borderless, non-activating, resizable floating panel (AppKit) with aspect-ratio-locked resize and drag-to-move.
- `Views/Preview/ScreenshotPreviewView.swift` — SwiftUI thumbnail hosted in the panel; reveals a row of circular action buttons (open in Finder, copy, edit-stub, drag-out-file) centered along the bottom on hover. When the capture wasn't saved to disk, Reveal in Finder is hidden and drag-out is backed by a temp PNG (`ScreenshotSaver.writeTemporaryPNG`, written by `ScreenshotPreviewController` at show time).
- `Views/Preview/HoverTrackingArea.swift` — `NSViewRepresentable` bridge providing hover detection that works while QuickSnap isn't the active app (see below).
- `Views/Settings/SettingsView.swift` — the `Settings` scene's root: `NavigationSplitView` sidebar (General/Markup/Hotkeys/Uploading/Advanced/About). All sections are built; `PlaceholderSettingsSection` is now unused but kept for future tabs.
- `Views/Settings/AdvancedSettingsView.swift` — Advanced tab. Deliberately **not** a power-user feature bucket (see the note under Non-obvious things): permissions status/troubleshooting, upload timeout and retries, retention, Copy Diagnostics (redacted), and Reset All Settings.
- `Views/Settings/SliderWithValue.swift` — the shared numeric row (slider + formatted readout) used by General and Advanced.
- `Views/Settings/UploadingSettingsView.swift` — Uploading tab: master toggle, provider picker, the selected provider's own section (`ImmichSettingsSection` / `S3SettingsSection`, private subviews in the same file), then the provider-neutral behaviour and button-visibility toggles. Each provider section builds credentials from the *typed* values rather than from `AppSettings`, so Test connection and album loading work before the settings are committed to a working state. Secrets go straight to the Keychain on change.
- `Views/Settings/MarkupSettingsView.swift` — Markup tab: default color (the toolbar's preset swatches + a hex-bridged `ColorPicker`), default stroke size as a *step index* into the per-image preset ladder (absolute pixels would read differently across capture sizes — the squiggle-weight buttons mirror the toolbar), and the four toolbar output-button toggles (Copy / Save / Save As… / drag-out — the last enabled one is disabled so at least one export path always remains).
- `Views/Settings/HotkeysSettingsView.swift` — Hotkeys tab: one `HotkeyRecorderField` per action (click to record via a local `NSEvent` key monitor: Esc cancels, Delete clears, invalid combos beep; assigning a combo used by another action clears it there). `HotkeyShortcut(event:)` decides validity: printable key + at least one of ⌘⌥⌃, or a function/navigation key alone.
- `Views/Settings/GeneralSettingsView.swift` — General tab: save-folder row (`NSOpenPanel` Choose…, Reset back to default), the After screenshot Show/Copy/Save checkboxes, the Notifications section (top/bottom position picker shared by preview panel and toast, plus separate auto-dismiss duration sliders for each — numeric rows share the `SliderWithValue` subview), the Text Recognition toast-preview toggle, and the Window Screenshots section (background style segmented picker, padding slider, solid-color ColorPicker bridged to the stored hex string). Uses `@AppStorage` with `AppSettings.Keys`/`Defaults`.
- `Views/ToastView.swift` — the toast pill's SwiftUI content (icon + message on a material capsule); `ToastController` owns presentation and timing.
- `Views/Motion.swift` — house motion style (full rationale in `docs/motion-design.md`): `Motion.panelSpring`/`Motion.revealSpring` (critically damped springs), `Motion.reduceMotion` (AppKit-side Reduce Motion check for coordinators; SwiftUI views use `@Environment(\.accessibilityReduceMotion)` instead), and `PressScaleButtonStyle` (press-down scale feedback — use it instead of `.plain` on icon buttons).
- `Views/Annotation/ToolbarIconButton.swift` — circular icon button shared by `MarkupToolbar` and `CropOverlay`'s confirm bar: hover highlight, press-down scale, accent-tinted active state. New toolbar-style buttons go through this rather than hand-rolling the 28×28 circle.
- `Views/ContentView.swift` — leftover from the SwiftUI template, currently unused. Kept as a starting point if a Preferences/About window is added later.

## Non-obvious things

- **Immich has no client-selectable folder — the destination is an album.** `POST /api/assets` has no folder/path field, and Immich's Folders view (`GET /api/view/folder`) is *read-only*: it browses by `originalPath`, which the server assigns from its own admin-configured storage template. The only grouping the API exposes to clients is the album (`PUT /api/albums/{id}/assets`), which is why Settings → Uploading offers an album picker and not a folder chooser. Don't re-litigate this without re-reading the spec (`open-api/immich-openapi-specs.json` in the immich repo — pull it directly, secondhand docs are unreliable). Other verified details: the upload response's `status` is `created` **or** `duplicate` (checksum dedupe); `deviceAssetId`/`deviceId` are sent for old-server compatibility and are safe because Immich validates with non-strict Zod objects, which strip unknown keys rather than rejecting them. Full write-up in `docs/uploading.md`.
- **`Config/Info.plist` exists solely for App Transport Security** (`NSAllowsLocalNetworking`, so a LAN Immich or MinIO over plain `http://192.168.x.x:2283` isn't blocked; public hosts still require HTTPS). Two constraints on it: it lives *outside* `QuickSnap/` because that folder is a synchronized group and an `Info.plist` inside it would also be copied in as a bundle resource; and `GENERATE_INFOPLIST_FILE` stays `YES`, with Xcode merging the `INFOPLIST_KEY_*` build settings on top — so only keys that can't be expressed as a flat build setting belong in the file.
- **Settings → Advanced is a support page, not a power-user bucket.** Anything a user would go looking for belongs on the page it relates to — filename templates and image format live in General beside the save folder, because burying them would hurt discoverability. Advanced holds only what is *diagnostic or destructive*: permission status, upload timeout/retries, retention, redacted diagnostics, and reset. Resist adding features there just because they feel advanced.
- **Retention only ever deletes files QuickSnap tagged.** `FileTag` writes an extended attribute on every saved file and `SaveFolderCleaner` refuses to consider anything without it, never recurses, and uses the Trash rather than `removeItem`. The save folder is user-chosen and the app is unsandboxed, so this is the property that makes the feature acceptable at all. If the attribute is lost the file is kept — retention under-deletes by design.
- **A JPEG request silently stays PNG when the capture has alpha** (`ScreenshotSaver.effectiveFormat(for:)`), because a transparent window capture flattened onto black is never what someone wants. Relatedly, annotation drag-out is always PNG: `AnnotatedFileDrag` declares a *static* `exportedContentType`, so the file has to match what the drop destination was promised.
- **Xcode project uses synchronized file groups** (`PBXFileSystemSynchronizedRootGroup`, Xcode 16+). Any `.swift` file placed anywhere under `QuickSnap/` (including new subfolders) is automatically part of the target — no `project.pbxproj` editing needed when adding or moving files. Only build *settings* changes require touching the project file (use the `xcodeproj` Ruby gem, already installed, rather than hand-editing).
- **App Sandbox is disabled** (`ENABLE_APP_SANDBOX = NO`). This is required so the app can write directly to `~/Documents/QuickSnap` without a save panel on every capture. Consequence: this app cannot be Mac App Store-distributed as-is; that would require switching to user-selected-folder + security-scoped bookmarks.
- **`LSUIElement = YES`** hides the Dock icon (menu-bar-only app). There is no other window; `WindowGroup`/`ContentView` were removed from the app entry point.
- **Never do TCC-gated file I/O on the main thread.** The first access to a privacy-protected folder (~/Documents, ~/Desktop, ~/Downloads, ~/Pictures — sandbox off doesn't exempt us) blocks *inside the file syscall* until the user answers the system consent prompt. Doing that on the main thread mid-capture froze the app under its own full-screen overlay windows badly enough to require a machine restart (2026-07). Rules now in place: `ScreenshotSaver`/`AppSettings`/`WindowBackgroundRenderer` are `nonisolated` enums; saves and wallpaper reads run in `Task.detached`; and every capture entry point calls `prepareSaveFolderAccess()` (which touches the save folder off-main) *before* any overlay window is shown, so a first-run prompt appears while the app is responsive and nothing covers the screen. Keep all three properties for any new file-touching feature.
- **Global hotkeys use Carbon `RegisterEventHotKey`** — the one non-deprecated piece of Carbon and the only supported system-wide hotkey API (it's what all the hotkey libraries wrap). It needs no Accessibility/Input Monitoring permission and *consumes* the keystroke system-wide, which is also why the `.keyboardShortcut` hints on the MenuBarExtra items can never double-fire: SwiftUI never sees the event. The C event handler callback gets `self` back via an `Unmanaged` userData pointer and uses `MainActor.assumeIsolated` (Carbon delivers on the main event loop). F-keys/arrows can't be shown as SwiftUI menu hints (`KeyEquivalent` is character-only) — those shortcuts still work, they just show no hint in the menu.
- **Screen Recording permission**: checked/requested in `ScreenRecordingPermission` (`Services/ScreenCaptureManager.swift`). macOS frequently doesn't recognize a freshly-granted permission for an already-running process — the denial alert tells the user to relaunch QuickSnap after granting access in System Settings. This is expected, not a bug.
- **Coordinate spaces**: `SelectionOverlayView` overrides `isFlipped = true` so its local view coordinates (top-left origin, points) match `SCStreamConfiguration.sourceRect`'s coordinate space directly — no manual flip needed when turning a drag rect into a capture request. Window-mode candidate frames (`SCWindow.frame`, which is in global Quartz top-left-origin coordinates) are converted to the same per-screen-local space by subtracting `CGDisplayBounds(displayID).origin` — see `startOverlaySession` in `CaptureCoordinator`.
- **Capture flow**: one `SelectionOverlayWindow` per connected `NSScreen` is created for every Area/Window session, all shown at once (so you can drag/click on whichever screen you're using); the rest are torn down as soon as one produces a result or the session is cancelled (Esc). The overlays are **non-activating `NSPanel`s** (`.nonactivatingPanel`, `hidesOnDeactivate = false`) so they can take key status for Esc without `NSApp.activate` — activating the app raised any open annotation/Settings windows above the app being captured and left them there (fixed 2026-07). Don't reintroduce an activate call on the capture path.
- **Preview panel** (`ScreenshotPreviewPanel`) uses `.nonactivatingPanel` + `canBecomeKey == false` so it can be dragged/resized/clicked without stealing focus/key-window status from whatever app is frontmost — same pattern as HUD/tooltip panels elsewhere in AppKit. It's also draggable (`isMovableByWindowBackground`) and resizable with `contentAspectRatio` locked to the screenshot's aspect ratio, like a video PIP window.
- **Hover detection must not use SwiftUI's `.onHover`** on the preview panel — that modifier tracks with `.activeInActiveApp`, which never fires while QuickSnap isn't the frontmost app (the normal case here, since the panel floats passively over whatever app the user was already using). `HoverTrackingArea` wraps a manual `NSTrackingArea` with `.activeAlways` instead. This applies to any future non-activating-panel UI, not just this one.
- **Cursor changes on the preview panel must not use `NSCursor.set()` in mouseEntered/mouseExited.** That approach sticks "until you or the window server changes it" per Apple's docs, and reliably goes stale after the user interacts with another app's window and comes back. `HoverTrackingArea` instead uses the `.cursorUpdate` tracking-area option + `cursorUpdate(with:)`, which AppKit itself re-invokes as needed and survives focus changes.
- **Window-background dragging/resizing bypasses `mouseDown`/`mouseUp` overrides on the window and its content views** — AppKit/the Window Server handles it before those reliably fire. `ScreenshotPreviewPanel` tracks mouse-down/up state via app-level `NSEvent` local monitors instead, and only considers a *drag* to have actually started once the frame visibly changes (`NSWindow.didMoveNotification`/`didResizeNotification`) while the mouse is still down — a plain click never moves the frame, so it doesn't trigger drag-only behavior (hiding the action bar, closed-hand cursor). Note those notifications fire synchronously from inside AppKit's tracking loop, so mutating SwiftUI `@Published` state directly from that callback doesn't animate — bounce through `DispatchQueue.main.async` first (still prompt; GCD main-queue dispatch is serviced during tracking loops, unlike a plain `Timer`).
- **The preview panel's auto-dismiss timer is hover-aware and interaction-permanent**: it pauses while hovered and restarts fresh on mouse-exit (so the dismiss fade can't start mid-way through the action bar's hide animation), and once the panel has actually been interacted with (`onInteractionBegan` — any mouseDown: click, drag-start, resize-start), auto-dismiss is disabled for that panel instance permanently. See `hasInteracted` in `ScreenshotPreviewController`.
- **No public API exists to opt an `NSWindow`/`NSPanel` out of macOS Sequoia's edge-drag window tiling/snapping.** Confirmed via an Apple Developer Forums thread ("Opt out of window tiling (macOS 15)") where a developer with the same problem got no working answer; Apple's own Sequoia AppKit guidance only covers tuning `minSize`/`resizeIncrements` for how tiling resizes your window, not whether it's eligible at all. `ScreenshotPreviewPanel.collectionBehavior` sets `.fullScreenDisallowsTiling`, which is a real, documented flag — but it only opts out of the older Split View full-screen tiling, not the newer edge-drag snap. If this becomes a real problem, the only other lever available is dropping `.resizable` from the style mask and reimplementing resize manually, which is unconfirmed to even help and hasn't been attempted.
- **Preview panel stays on the Space it was created on, and is not Mission-Control-draggable — this is an intentional trade-off, not an oversight.** `collectionBehavior` has no `.canJoinAllSpaces` (so it doesn't follow you to every Space) and no `.managed` (so it doesn't try to participate in Mission Control's per-Space tile view). Mission Control's "drag a window's tile to another desktop" gesture only works for `.normal`-level, Spaces-managed windows — `NSWindowCollectionBehavior.managed` is the *default* specifically for `NSNormalWindowLevel` windows. Our panel is deliberately `level = .floating` so it stays visible above whatever app is frontmost; a `.floating`-level window can't be made a draggable Mission Control tile without dropping to `.normal` level, which would let other apps' raised windows cover it and defeat the whole point of a persistent PIP overlay. Asked and confirmed with the user (2026-07) — keep `.floating`, don't revisit this trade-off without checking again.
- **Markup tools use PaperKit's canvas (`PaperMarkupViewController`) with a fully custom SwiftUI toolbar — Apple's `MarkupToolbarViewController` is deliberately not used.** Native macOS PencilKit has **no `PKCanvasView` and no `PKToolPicker`** (those are UIKit/Catalyst-only); it only ships the data model (`PKDrawing`, `PKInkingTool`, `PKEraserTool`, `PKLassoTool`) plus rendering. PaperKit is the macOS route to PencilKit drawing. The custom toolbar drives the canvas via `drawingTool: any PKTool` (settable), `indirectPointerTouchMode` (`.drawing` vs `.selection` — this is what decides whether mouse input draws or selects, so "Select" is a mode flip, not a tool), and shape/line/text insertion by mutating a copy of `markup` (`PaperMarkup.insertNewShape/insertNewLine/insertNewTextbox`) and assigning it back. Shapes and lines are drag-to-create: the toolbar's shape row arms `pendingInsertion`, `ShapeInsertionOverlay` captures the drag with a live preview (Esc or a bare click cancels), and the dragged geometry is inserted in canvas pixel coordinates (view points × zoom-to-fit scale; PaperKit's canvas is UIKit-based, so top-left origin matches SwiftUI directly). Only text still uses `suggestedFrameForInserting`.
  - An earlier PaperKit attempt was reverted: it hosted `PaperMarkupViewController` + `MarkupToolbarViewController` in a raw `NSViewController` set as `window.contentViewController` with Auto Layout, and fought window sizing continuously (several real constraint bugs, plus a never-root-caused narrow-window bug). The working approach hosts the canvas via **`NSViewControllerRepresentable` inside SwiftUI** — SwiftUI owns layout, no Auto Layout contact surface. Don't reintroduce the `contentViewController`/Auto Layout combination.
  - `PaperMarkupViewController` is `public` but **not `open`** — it can't be subclassed, so zoom-to-fit is done by observing `NSView.frameDidChangeNotification` on its view (pinning `zoomRange` to the fit scale + `setContentVisibleFrame`) rather than overriding `viewDidLayout()`.
  - Ground-truth API for PaperKit/PencilKit (secondhand docs were incomplete/inconsistent) is the installed SDK's `.swiftinterface` files under `.../MacOSX.sdk/System/Library/Frameworks/{PaperKit,PencilKit}.framework/Versions/A/Modules/*.swiftmodule/` — read those directly. Key shape: background image goes in `PaperMarkupViewController.contentView` (not part of `PaperMarkup`); `FeatureSet.latest` covers all shape/text/drawing tools; `PaperMarkup.draw(in:frame:)` is the flatten/export API (macOS 26.0+).
  - Canvas coordinates equal the screenshot's **pixel** coordinates (markup bounds = image pixel size), so stroke widths/text sizes are in image pixels — `MarkupCanvasController` scales its width range with image size — and export composites at full resolution with no scaling.
  - **`PaperMarkup.draw(in:frame:)` does not flip for you.** Canvas coordinates are top-left origin (PaperKit is UIKit-based), but `draw` renders straight into the `CGContext`'s own bottom-left-origin space, so markup comes out mirrored about the image's horizontal centerline (text upside-down) unless the CTM is flipped first. `exportFlattened` draws the base image unflipped, then flips inside a `saveGState`/`restoreGState` pair for the markup pass. Verified with a standalone `swift` script rendering a known-position shape (2026-07) — the flip is *not* documented anywhere in the `.swiftinterface`.
- **Crop is a real, annotation-preserving crop, not an export-time mask.** `PaperMarkup.bounds` is settable and `transformContent(_:)` translates all existing markup, so `MarkupCanvasController.applyCrop` cuts the base image (`CGImage.cropping`, same top-left-origin pixel space as the canvas), shifts the markup by the crop origin, and shrinks `bounds` — prior annotations stay individually editable in place. `baseImage`/`canvasBounds` are `@Published`; `MarkupCanvasView` reacts in `updateNSViewController` by swapping the contentView image and force re-fitting the viewport (the frame-change observer reads `canvasBounds` from the controller at notification time, never captures it). The aspect-ratio change flows out via `AnnotationView`'s `onCanvasAspectChanged` closure → `AnnotationCoordinator.canvasAspectChanged`, which re-locks `windows[window]`, updates `contentMinSize`, and animates the window to a conforming frame (top-left anchored, clamped to the screen) — deferred through `DispatchQueue.main.async` because it fires from a SwiftUI `onChange` during view update. Crop is not undoable (neither are programmatic insertions — PaperKit's undo only covers user canvas edits).
- **Zoom/pan state lives in `visibleCanvasFrame`** (`MarkupCanvasController`, image-pixel coordinates): pinch/scroll gestures are handled entirely inside the remote PaperKit process, so the *only* way the host app learns about them is `PaperMarkupViewController.Delegate.paperMarkupViewControllerDidChangeContentVisibleFrame` — the controller is that delegate and republishes `contentVisibleFrame` as a **pure observer** (it never corrects incoming reports; that lost, see below). Everything that maps view points → canvas pixels (`ShapeInsertionOverlay`, `CropOverlay`) must go through `visibleCanvasFrame` (origin offset + uniform scale), never assume fit. Zoom is gesture-only by design — toolbar zoom buttons were added and removed (2026-07); don't reintroduce them without asking.
- **Window resizes preserve the *relative* zoom via verify-and-retry enforcement** (`MarkupCanvasView.Coordinator.enforceViewport`). PaperKit's default keeps absolute scale on a viewport resize (silently zooming in as the window shrinks) and has no fit/content-mode API — `zoomRange` + `contentVisibleFrame` is its entire zoom surface (checked the `.swiftinterface`). Two theorized designs failed against real behavior (probe, 2026-07) — the facts that killed them, all empirically established:
  - The remote canvas **freezes its zoom during a live resize and silently drops ALL host→remote sets** (`zoomRange` and `setContentVisibleFrame` both — likely `NSRemoteView` suspending sync), resuming at an unknowable moment after the drag ends. One-shot sets at `didEndLiveResize` are unreliable; retry-until-verified is the only dependable pattern.
  - A set whose zoom falls outside the remote's *current* (possibly stale) range is **clamped, sometimes into a silent no-op** — no delegate response at all. Enforcement re-sends the range before the frame on every attempt.
  - Remote delegate reports are **indistinguishable from user gestures** — correcting "suspect" incoming reports (the settle-window design) ate legitimate zooms and locked drift in.
  - Enforcement must verify against `lastRemoteReport` (nil until the remote's first report), **never `visibleCanvasFrame`**, whose initial value is a local assumption — trusting it made enforcement converge before the remote initialized, leaving the canvas at default zoom instead of fit.
  - Flow: `NSWindow.willStartLiveResizeNotification` (fires *before* any size change) captures the region to restore; `didEndLiveResizeNotification` starts enforcement toward it. Programmatic resizes (initial layout, post-crop animation, title-bar zoom button) enforce from the frame-change observer; steps of an ongoing animation don't restart an active enforcement. 4 s deadline as escape hatch for unsatisfiable targets (convergence is normally <200 ms).
- **Zoom-resize probe** (`Probe/ZoomResizeProbe.swift`; run `QUICKSNAP_ZOOM_PROBE=1 <DerivedData>/…/QuickSnap.app/Contents/MacOS/QuickSnap` from a terminal): opens an annotation window with a synthetic image at launch, performs real live-resize drags via CGEvents (needs Accessibility for QuickSnap — it checks `AXIsProcessTrusted` and does a control drag first), logs every zoom decision with timestamps, prints PASS/FAIL per scenario, then terminates. Inert without the env var. This is how the facts above were established — re-run it after touching any viewport/zoom code, and extend its scenarios rather than theorizing about remote-canvas timing.
- **The PaperKit canvas is an ExtensionKit REMOTE view** (`_EXHostView`/`NSRemoteView`; the actual canvas UI runs in `PaperKitExtension.appex`, a Catalyst process). Three non-negotiable consequences, all confirmed empirically (2026-07):
  - **Input routing over the canvas is decided by whether a layer above it actually RENDERS PIXELS, not by SwiftUI hit-testing** (confirmed empirically 2026-07, both directions). A `.overlay` that draws anything — even a 1 px decorative stroke with `.allowsHitTesting(false)` — silently kills ALL canvas mouse input (no drawing, no selection, no cursor changes; rendering and programmatic markup keep working): the window server sees the remote surface as occluded and stops routing input to the extension process, and SwiftUI's hit-testing opt-out doesn't exist at that level. Conversely, a **non-drawing** overlay (`Color.clear` + `contentShape` + gesture) does nothing at all: input keeps flowing straight to the extension process, bypassing the host app's responder chain, so the local gesture never fires either. Consequences: decorations must go in `.background` (the hairline border in `AnnotationView` is drawn behind, outset by 1 px) — `clipShape`, `aspectRatio`, `padding`, material backgrounds, and VStack siblings are all safe; and any overlay that *wants* to capture input (like `ShapeInsertionOverlay`, mounted only while a shape/line insertion is armed) must render something visible — it uses a 15% black dim, which both flips the input routing to the host app and signals the mode to the user.
  - **In-process synthetic events (`window.sendEvent`) never reach the canvas** — to exercise it programmatically, post real `CGEvent`s (`.cghidEventTap`); verify event delivery first with a control test (e.g. drag the title bar and check the window moved), since CGEvent posting silently no-ops without Accessibility permission. (A temporary env-gated probe using this technique — open an annotation window with a synthetic image at launch, CGEvent-drag the canvas, compare `markup` before/after — was how this class of bug was reproduced and verified; rebuild it if canvas input ever regresses.)
  - The background `NSImageView` set as `contentView` overrides `hitTest` → `nil` (`HitTestTransparentImageView`) — PaperKit's contentView pattern assumes iOS's non-interactive-by-default `UIImageView`.
- **Swift 6.2 upcoming-features gotchas** (this target enables `InferIsolatedConformances`, `MemberImportVisibility`, default-isolation `MainActor`): a `@MainActor` class's `ObservableObject` conformance is inferred *isolated* and then fails `@StateObject`'s generic constraint with a misleading "does not conform to protocol" error — declare it `final class Foo: nonisolated ObservableObject`. And `@Published` needs an explicit `import Combine` (SwiftUI's re-export isn't enough under `MemberImportVisibility`).
- **Annotation windows are standard, titled `NSWindow`s** (`styleMask = [.titled, .closable, .resizable, .miniaturizable]`) — native title bar, native traffic-light close button, native resize. A fully custom borderless window (own pseudo title-bar pill, own drag-to-move via a SwiftUI `DragGesture`, own close button, a `canBecomeKey` override since borderless windows default that to `false`) was tried first and reverted after repeatedly fighting us: the custom drag handler was jittery (SwiftUI's `DragGesture` `.global` coordinate space is relative to the window itself, so translation deltas fed back into moving that same window create a feedback loop — screen-space deltas from `NSEvent.mouseLocation` are what's actually needed for this kind of "drag this view to move its own window" logic), and a resize-related layout bug was never root-caused. Letting AppKit's native window chrome handle title bar/close/resize/drag removed that whole class of bug at once; only the markup tools pill remains bespoke SwiftUI. Multiple annotation windows can be open at once; `AnnotationCoordinator` is not a singleton-panel controller like `ScreenshotPreviewController`.
- **The annotation window's title bar blends into the content via `.fullSizeContentView` + `titlebarAppearsTransparent`** — but `.fullSizeContentView` alone is not enough with an `NSHostingView` content view: the hosting view still reports a safe-area inset for the title-bar region to its SwiftUI content, so content stops short of the top. The working recipe is `hostingView.safeAreaRegions = []` (set **after** attaching the hosting view to the window — safe-area computation is derived from the window context and setting it beforehand didn't fully take effect) plus `.ignoresSafeArea(.container, edges: .top)` in the SwiftUI root. The mat's top padding (`AnnotationView.Layout.matTopPadding`) is what keeps the canvas clear of the traffic lights. An earlier attempt without the safe-area fix broke sizing badly and was reverted.
- **Annotation window resizing is aspect-ratio-locked in the window delegate, not via `contentAspectRatio`.** The correct window shape is "canvas at the image's aspect ratio + a fixed chrome offset" (mat padding + toolbar pill: `AnnotationView.Layout.chromeSize`), and `NSWindow.contentAspectRatio` can only express a pure ratio, no constant offset. `AnnotationCoordinator.windowWillResize(_:to:)` constrains user resizes (the axis being dragged more drives, the other follows), `windowWillUseStandardFrame` handles the zoom button, and `contentMinSize` + the initial size are computed with the same math — so the mat and toolbar always line up exactly with the window edges. The lock holds regardless of the canvas's internal zoom/pan (the viewport's shape always matches the image); a free-resize/letterbox design was tried when zoom landed and reverted the same day (2026-07) — the tight frame is deliberate. If the layout paddings/toolbar height in `AnnotationView`/`MarkupToolbar` change, `Layout.chromeSize` must stay in sync or the lock drifts.

## Conventions

- Saved filenames come from the user's template (`FilenameTemplate`), defaulting to `QuickSnap yyyy-MM-dd at HH.mm.ss` plus the configured format's extension, in the configured save folder (default `~/Documents/QuickSnap`).
- After a capture, up to three actions run per the General settings toggles (all on by default): save to disk, copy to clipboard, show the bottom-right preview panel.
- No capture sound (deliberately not implemented — revisit if wanted).
- Motion: critically damped springs by default via `Motion` constants (no overshoot unless a gesture carried momentum); enter/exit mirror the same path; every slide/scale degrades to a cross-fade under Reduce Motion; gesture-tracked geometry (crop rect, area selection) is never animated. Details in `docs/motion-design.md`.

## Build

```
xcodebuild -project QuickSnap.xcodeproj -scheme QuickSnap -configuration Debug build
```

Or open `QuickSnap.xcodeproj` in Xcode and run the `QuickSnap` scheme. Deployment target is macOS 26.5 (uses `SCScreenshotManager`, available since macOS 14).
