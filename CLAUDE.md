# QuickSnap

Menu bar screenshot utility for macOS (area / window / full screen), inspired by CleanShot X. Captures via ScreenCaptureKit, auto-saves to `~/Documents/QuickSnap`, and copies to the clipboard.

## Project structure

```
QuickSnap/
  QuickSnapApp.swift     — app entry point (MenuBarExtra scene)
  Views/                 — UI only: NSWindow/NSPanel/NSView/SwiftUI View subclasses
    Overlay/               (Area/Window selection overlay)
    Preview/               (post-capture PIP thumbnail)
    Annotation/            (screenshot editor window — PaperKit markup canvas + custom toolbar)
    Search/                (Spotlight-style capture search panel)
    Settings/              (Settings window — sidebar + per-section detail views)
    Onboarding/            (first-run setup flow)
  Coordinators/           — owns state and window/panel lifecycles; wires Views to Services
  Services/               — stateless operations: ScreenCaptureKit calls, file I/O, permissions
  Assets.xcassets/        — app icon, accent colour, generated option thumbnails
Tools/                    — developer scripts run by hand; outside QuickSnap/ so the
                            synchronized group doesn't compile them into the target
```

Each feature area (capture overlay, preview thumbnail, ...) gets its own subfolder under `Views/` if it has more than one file. `Coordinators/` and `Services/` stay flat unless one grows enough files to warrant grouping.

### Layering rules — follow these for new work

1. **Views own no business logic.** An `NSView`/`NSWindow`/`NSPanel`/SwiftUI `View` may track its own transient UI state (e.g. a drag rect, a hover highlight) but reports results outward via a delegate protocol or closure. It never calls a Service directly, never knows about `ScreenCaptureKit`, file paths, etc. The one carve-out is a **pure pixel transform** with no I/O, no policy and no state — `MarkupCanvasController` calls `Redactor.redacting` the same way it calls `CGImage.cropping`, because routing an image-in/image-out function through a closure buys indirection and nothing else. Anything that decides *whether* or *when* (running the detector, reading settings, touching disk) still goes through a Coordinator.
2. **Coordinators own lifecycles and state.** They create/show/dismiss windows and panels, hold the delegate/closure callbacks from Views, call into Services, and decide what happens next (open a file, show an alert, chain into another capture step). A Coordinator can own multiple related Views (e.g. `CaptureCoordinator` owns one `SelectionOverlayWindow` per screen).
3. **Services are stateless and UI-agnostic.** They take plain inputs and return values or throw — no window/view references, no stored mutable state beyond simple caches. This is what makes them independently reasoned-about and, eventually, testable.
4. **One primary type per file, file name matches the type.** Small tightly-coupled support types (an error enum, a small struct only used by one file) can stay in that same file rather than being split out — don't fragment for its own sake.
5. Adding a new capture mode or feature: put its view(s) in a new `Views/<Feature>/` folder, its orchestration in `Coordinators/`, and any new primitive operations in `Services/`. Thanks to Xcode's synchronized file groups (see below), no project file editing is needed — just create the file in the right folder.

## Architecture

- `QuickSnapApp.swift` — `MenuBarExtra` entry point (menu-only, no window). Owns a single `CaptureCoordinator` as `@StateObject`.
- `Coordinators/CaptureCoordinator.swift` — orchestrates capture: permission checks, opening/closing the per-screen overlay windows, running the actual capture, then the after-capture actions per `AppSettings` (save / copy / show preview, each individually toggleable), and error alerts. Overlay sessions carry a `SelectionSessionKind` (`area` / `window` / `textRecognition` / `copyForAI`): the two clipboard-only kinds reuse the area overlay but route the rect elsewhere, and for both the after-screenshot toggles deliberately don't apply — the clipboard *is* the output, so nothing is saved or previewed and `writesToSaveFolder` skips the save folder's TCC warm-up. OCR goes to `recognizeTextInArea` (Vision OCR → text to clipboard → toast); Copy for AI goes to `copyContextForAI` (capture → optional OCR → temp PNG → image *and* `CaptureContextMarkdown` on one pasteboard item → toast). See `docs/intelligence.md`. When Save is off, no file is written and a `CaptureFile` with a nil URL flows through the preview and annotation layers: the preview hides Reveal in Finder and backs drag-out with a temp PNG instead; the annotation window falls back to timestamped naming. When the template uses `{describe}`, `describeAndRename` runs after the save and moves the file (see Non-obvious things).
- `Coordinators/HotkeyCoordinator.swift` — owns the global hotkey registrations (Carbon `RegisterEventHotKey`) and re-applies them whenever UserDefaults changes (diffed against the last-applied set, since that notification fires on every defaults write). Dispatches through an `onAction` closure wired by `CaptureCoordinator`, which also calls `AppSettings.registerDefaultHotkeys()` at init.
- `Coordinators/ToastController.swift` — transient confirmation pill (centered at the top or bottom edge per `AppSettings.toastPosition`, non-activating, click-through, auto-dismiss ~2s). Takes an optional `detail` line — the OCR flow passes the copied text (two-line truncation in `ToastView`), gated by the `showTextPreviewInToast` setting. Reuse it for any future "did the thing" feedback. Under `toastPosition == .notificationCenter` the same calls are handed to `SystemNotifier` instead of drawing a pill — one setting covers OCR, upload results and annotation saves alike, because they all come through here. The pill is measured with `NSHostingController.sizeThatFits(in:)` proposing `ToastView.Layout.maxWidth`, **not** `NSHostingView.fittingSize` — that property is a *minimum* size, so wrapping text collapses to its narrowest layout and even a short detail came back wrapped and truncated. That proposal is also the only thing capping the detail's line length; a `.frame(maxWidth:)` on the text can't do it, because a flexible frame grows to fill the proposal and pads every toast out to full width.
- `Coordinators/ScreenshotPreviewController.swift` — owns the floating post-capture thumbnail panel's lifecycle: show, animate in/out, auto-dismiss timer (cancelled on drag/resize/any action button press), and wires the panel's action closures (open in Finder, copy, edit) to Services. `show(...)` takes an `onEdit` closure from its caller rather than knowing what "Edit" does itself. Placement follows `AppSettings.previewPosition`: a trailing top/bottom corner, or — under `.dynamic` — centered on the `anchor` rect the caller passes (the captured region in AppKit global coordinates), clamped into `visibleFrame`. A nil anchor means a full-screen capture and falls back to the bottom corner.
- `Coordinators/AnnotationCoordinator.swift` — opens/owns annotation windows (one per screenshot being viewed/edited, not a singleton like the preview panel). Toggles `NSApp.activationPolicy` between `.accessory` and `.regular` while any annotation window is open. Wires the annotation window's output actions: Copy → `ScreenshotSaver.copyToClipboard`, Save → `ScreenshotSaver.save` into the configured folder + toast confirmation (owns its own `ToastController`), Save As… → `NSSavePanel` sheet + `ScreenshotSaver.writePNG`. The original screenshot file is never overwritten. Both save paths end in `closeAfterSaveIfEnabled`, which closes the window when `AppSettings.markupClosesAfterSave` is on (the default) — read at save time, so an already-open window follows a settings change, and only ever after the write *succeeded*, so a failed save keeps the work and a cancelled Save As… does nothing. Also reads the Markup settings defaults (`AppSettings.markupDefaultColor`/`markupDefaultStrokeStep`) and passes them into `AnnotationView`, and owns the credential scan (`scanForSensitiveContent`) the toolbar's redact button triggers — `MarkupCanvasController` holds the findings but never calls the detector, because deciding *when* to run a Service is the coordinator's job.
- `Coordinators/OnboardingCoordinator.swift` — the first-run flow's window: a singleton (like `CaptureIndexer`, because the Settings scene reopens the same flow the capture path launches), `showIfFirstRun()` called from `CaptureCoordinator.init` before anything else user-facing, and the `.regular`/`.accessory` activation-policy dance while it's open. Closing the window counts as finishing — there's no half-completed state to nag about on the next launch, and `replay()` exists for the temporary Settings → General button. **Not** a gate: every step is skippable including the permission one.
- `Views/Onboarding/OnboardingView.swift` — the flow's root: the step enum, the footer (Back / Skip / Continue, progress dots centred by an `.overlay` on the footer rather than between spacers, since the buttons' widths differ and shift per step), and `OnboardingStepLayout`, the shared icon/title/message/content chrome. Steps are one file each: `OnboardingWelcomeStep` (what it is, and that it lives in the menu bar with no Dock icon — someone who doesn't know that has lost the app), `OnboardingPermissionStep` (Screen Recording, polled on a timer because the grant happens in System Settings with no notification, plus the relaunch caveat), `OnboardingSavingStep` (save folder + the three after-capture toggles; its `.task` also warms the save folder off-main, so the `~/Documents` TCC prompt is answered on a screen about saving rather than mid-capture), `OnboardingHotkeysStep` (reuses `HotkeyRecorderField`), `OnboardingToolbarStep` (embeds `MarkupToolbarEditor` as-is, so it can't drift from Settings), and `OnboardingFinishStep` (launch at login + the capture-indexing disclosure).
- `Services/ScreenCaptureManager.swift` — thin wrapper over ScreenCaptureKit (`SCScreenshotManager.captureImage`, a one-shot API — there is no live `SCStream`). Also holds the Screen Recording (TCC) permission helpers (`ScreenRecordingPermission`). Window captures set `ignoreShadowsSingleWindow` + `shouldBeOpaque = false` so the bare window comes back with rounded-corner alpha and no baked system shadow — `WindowBackgroundRenderer` owns presentation.
- `Coordinators/UploadCoordinator.swift` — owns the whole upload lifetime (PNG encode off-main → `UploadDestination.upload`) and all its user feedback, for **any** provider. Also the redaction gate: it's the one choke point every upload path already went through, so scanning there covers automatic, preview-panel and markup-toolbar uploads by construction (`docs/redaction.md`). Every upload path goes through here: automatic post-capture, the preview panel's button, and the markup toolbar's button. Progress is an `autoDismisses: false` toast replaced by a result toast; concurrent uploads are reference counted (`activeUploads`) so only the last to finish reports. Full reference in `docs/uploading.md`.
- `Services/UploadDestination.swift` — the provider protocol (`providerName` + `upload`) plus `UploadRequest`/`UploadOutcome` and the `UploadProvider` enum. Adding a provider = a conformer, an enum case, a settings section, and a branch in `AppSettings.uploadDestination`; nothing in the coordinator or the capture/preview/markup wiring changes, since they only hold an `any UploadDestination`.
- `Services/ImmichDestination.swift` / `Services/S3Destination.swift` — the two conformers. Immich orchestrates upload → album → shared link over `ImmichClient`; S3 is a single signed `PUT` against any S3-compatible endpoint (R2/B2/MinIO/Wasabi/Spaces/AWS), path-style or virtual-hosted, with S3 XML error codes translated to plain language.
- `Services/ImmichClient.swift` — stateless REST wrapper (Immich OpenAPI `3.1.0`, `/api` base, `x-api-key`): test connection, list/create albums, multipart upload, add-to-album, create shared link. Also owns `normalizedServerURL`, which tolerates a trailing `/`, a trailing `/api`, and a missing scheme (`http` for LAN addresses, `https` otherwise).
- `Services/AWSSignatureV4.swift` — hand-rolled SigV4 on CryptoKit (no SDK). **Verified against AWS's official test-suite vectors via a validated Python reference — re-run that rather than eyeballing changes; the procedure and the three bugs it caught are in `docs/uploading.md`.** Watch three things in particular: the canonical URI comes from `URLComponents.percentEncodedPath` because `URL.path` silently drops a trailing slash; the signed Host header must include a non-default port (`URL.host` omits it); and `uriEncode` is written by hand because `addingPercentEncoding` doesn't follow AWS's unreserved set or uppercase hex.
- `Services/KeychainStore.swift` — generic-password wrapper. Secrets (the Immich API key, the S3 secret access key) live here, never in UserDefaults; `AppSettings` joins them with the stored non-secret config.
- `Services/ScreenshotSaver.swift` — encode (`imageData`, the one encoder shared by disk writes, drag-out files and uploads), write to the configured save folder (`save`) or a specific URL (`write`), rename in place (`rename`, a move so the `FileTag` xattr survives), temp files, clipboard copy. Names come from `FilenameTemplate`; collisions get a numeric suffix; every file written is tagged via `FileTag`. `saveDirectory` delegates to `AppSettings.saveFolder`.
- `Services/FilenameTemplate.swift` / `Services/ImageFormat.swift` — token-based naming (`{date}`, `{app}`, `{window}`, `{counter}`, `{describe}`…) and the PNG/JPEG/HEIC enum. The default template reproduces the original hardcoded convention byte for byte. Also holds `ResolvedFilename` (a name kept as its *inputs* so a `{describe}` rename re-renders identically — see Non-obvious things) and `slug`, the whitelist that turns model output into something safe to hand a filesystem call. `render` is deterministic: `counter` **and** `randomSuffix` are parameters, never generated inside. Full reference in `docs/files-and-retention.md`.
- `Services/CaptureAnalyzer.swift` — the one pass that reads a capture: Vision OCR plus (when intelligence is on and available) a prose description from `AIProvider`. Shared rather than per-feature, because on-device the description *is* the OCR plus the window it came from, so running Vision twice would buy nothing. Never throws — both halves are enrichment and callers fall back to their non-AI behaviour.
- `Coordinators/CaptureFile.swift` — a reference box holding where a capture currently lives on disk, observed by the preview panel and the annotation window so they follow a `{describe}` rename instead of pointing at a path that no longer exists.
- `Services/FileTag.swift` / `Services/SaveFolderCleaner.swift` — the retention pair. Every file QuickSnap writes gets an extended attribute, and the cleaner only ever deletes files carrying it (to the Trash, non-recursively). This is what makes "delete captures after N days" safe in a user-chosen folder on an unsandboxed app — **don't replace the xattr check with filename matching**, which was considered and rejected as fragile.
- `Services/SystemNotifier.swift` — Notification Center delivery, the alternative presentation for every confirmation when `toastPosition` is `.notificationCenter`. `ToastController` is the only caller, so the rest of the app keeps calling one API and never knows which presentation it got. Not a bare enum like its neighbours for two reasons: `UNUserNotificationCenter` holds its delegate weakly, and **without a delegate returning `[.banner, .list]` from `willPresent`, macOS suppresses the banner whenever QuickSnap is frontmost** — which it is while an annotation window is open, so Save confirmations would silently vanish. Posting always attempts and reports back: `add` fails with `UNErrorCodeNotificationsNotAllowed` when permission was never granted or has been revoked, and `ToastController` falls back to the pill so a confirmation is never lost. In-progress states (`autoDismisses: false`) are skipped entirely — a banner can't be updated in place or taken back, so "Uploading…" would outlive the upload.
- `Services/LoginItem.swift` — `SMAppService.mainApp` wrapper. Registration state lives with the system, not UserDefaults, so `isEnabled` re-reads `status` every time (the user can revoke it in System Settings).
- `Services/AppSettings.swift` — UserDefaults-backed settings: custom save folder path (falls back to `~/Documents/QuickSnap` when unset or the folder no longer exists), the three after-screenshot toggles (show preview / copy / save, all default true), the window background options (`WindowBackgroundStyle` enum, padding in points, solid color stored as `#RRGGBB` via the `NSColor` hex extension in the same file), `NotificationPosition` (where a transient panel appears; `previewPosition` and `toastPosition` are separate keys, both default bottom, and each picker offers its own subset — `previewCases` / `toastCases` — of one enum. `.dynamic` is preview-only and `.notificationCenter` toast-only, and *both* accessors map the other panel's case back to `.bottom`, so a value stored before the split, or migrated from the old shared key, can't reach code that has no meaning for it), per-panel auto-dismiss durations (preview 4.5s / toast 2.2s defaults, read at schedule time so changes apply to the next timer; the preview slider's max — `previewAutoDismissNeverThreshold` — means "Never": `previewAutoDismissSeconds` returns nil and no dismiss is scheduled), the OCR toast text-preview toggle, and the Markup settings (default color hex, default stroke step 0…`markupStrokeStepCount`-1, `markupClosesAfterSave`, and the four toolbar output-button visibility flags). `Keys`/`Defaults` constants are shared with the `@AppStorage` properties in the settings views (and `MarkupToolbar`'s visibility flags) — keep both in sync. `migrateLegacySettings()` (called once from `CaptureCoordinator.init`, before anything reads the new keys) carries stored values across key renames so a rename doesn't silently reset the user's choice; each migration is dated in a doc comment and can be dropped once no install can still be carrying the old key.
- `Services/HotkeyShortcut.swift` — `HotkeyAction` (the five actions, with default shortcuts ⌘⇧7/8/9 for area/window/full screen, ⌘⇧0 for OCR and ⌘⇧1 for Copy for AI — **not** ⌘⇧6, which macOS reserves for capturing the Touch Bar; `RegisterEventHotKey` fails silently on a shortcut the system already owns) and `HotkeyShortcut` (keyCode + modifier flags + human-readable key label, captured from an `NSEvent` at record time because deriving a label from a keyCode needs the live keyboard layout). Handles Carbon modifier conversion, the ⌃⌥⇧⌘ display string, and JSON persistence where empty `Data` means "explicitly cleared" vs. an absent key meaning "use the default" (defaults are *registered*, not written — see `AppSettings.registerDefaultHotkeys`).
- `Coordinators/MCPCoordinator.swift` — the MCP server: `NWListener` lifecycle on loopback, bearer auth, `Origin` validation, JSON-RPC dispatch, and the tool implementations. Drives capture through the `MCPCaptureHost` protocol (defined here, conformed by `CaptureCoordinator`) rather than reaching into it. Also holds `MCPToolError` and `MCPServerStatus`, the small observable the settings UI reads. Full reference in `docs/mcp.md`.
- `Services/MCPProtocol.swift` / `Services/HTTPMessage.swift` / `Services/JSONValue.swift` — the wire format, in pure functions: JSON-RPC framing plus the tool catalogue; just enough HTTP/1.1 for one endpoint; and a `Sendable` JSON tree (`[String: Any]` from `JSONSerialization` isn't, so it can't cross into the coordinator).
- `Services/CaptureLibrary.swift` — read access to the save folder as a list of captures. **Only ever surfaces files carrying the `FileTag` xattr**, so MCP clients can't enumerate or fetch files QuickSnap didn't write; `entry(named:)` rejects any name with a path separator rather than resolving it.
- `Services/CaptureIndex.swift` — the full-text index of the save folder: SQLite FTS5 through the system `libsqlite3` (`import SQLite3`, no package), one virtual table with `UNINDEXED` metadata columns, bm25 ranking and `snippet()`. An `actor`, not the usual stateless enum, because it owns a database connection. The database lives in Application Support — it's derived data, and the save folder is the user's. Full reference in `docs/search.md`.
- `Coordinators/CaptureIndexer.swift` — keeps the index in step with the folder: index-on-save (fed by the same `CaptureAnalyzer` pass `{describe}` uses), the cancellable backfill with progress, launch reconcile, and row removal when retention trashes files. A singleton, like `MCPServerStatus`, because the Settings scene drives the same indexer the capture path feeds.
- `Coordinators/CaptureSearchController.swift` — the search panel's lifecycle and `CaptureSearchModel` (debounced query → `CaptureIndex.search`, selection, recents when the field is empty). Reveal in Finder and open-for-markup are its two actions; the second goes out through an `onEdit` closure, same arrangement as the preview panel.
- `Views/Search/CaptureSearchPanel.swift` / `CaptureSearchView.swift` — the borderless HUD panel and its SwiftUI content. **The one panel in the app that takes key status** (a search box that can't be typed into is nothing) — see Non-obvious things for that and for why its keyboard handling is zero-sized buttons rather than `onKeyPress`.
- `Services/ImageResizer.swift` — proportional downscaling, used only for the images returned over MCP (full resolution goes back as a file path instead).
- `Services/AIProvider.swift` — the seam for "ask a model about a capture": the protocol (`providerName`, `availability`, and **narrow named tasks** rather than a free-form `prompt`), `AIAvailability`/`AIUnavailableReason`, and the request/error types. Same shape and rationale as `UploadDestination`. Adding a provider = a conformer plus a branch in `AppSettings.aiProvider`. Full reference in `docs/intelligence.md`.
- `Services/FoundationModelsProvider.swift` — the on-device conformer (Apple Foundation Models, macOS 26+, so unconditional at our deployment target). Guided generation via `@Generable`, greedy sampling, OCR input truncated to 4000 chars. **The system model takes no image input** — see the note under Non-obvious things.
- `Services/CaptureContextMarkdown.swift` — renders a capture plus its app/window/timestamp/OCR as the markdown block the Copy for AI action puts on the clipboard. Pure function, no I/O.
- `Services/TextRecognizer.swift` — on-device OCR via Vision's modern Swift API (`RecognizeTextRequest`, accurate + language correction + auto language detection). `recognizeText` returns lines joined with newlines; `recognizeLines` keeps each line's pixel-space frame **and a closure boxing an arbitrary substring** (`RecognizedText.boundingBox(for:)`), which is what lets redaction cover a token rather than the whole line.
- `Services/SensitiveContentDetector.swift` — regex classification of OCR'd text into `SensitiveMatch`es with pixel rects: credentials that **hold an upload** vs. things that are only flagged. Never keeps the matched text, only a masked preview. Pure and standalone-testable. Full reference in `docs/redaction.md`.
- `Services/Redactor.swift` — burns solid black boxes into a `CGImage`. Destructive by design: a shape drawn as markup is an object that can be moved, deleted or missed by an export path, which is not a redaction.
- `Services/WindowBackgroundRenderer.swift` — composites a Window-mode capture per `WindowBackgroundStyle`: pads the window out, draws a soft shadow shaped by the window's own rounded-corner alpha, and fills the background with wallpaper (aspect-fill of `NSWorkspace.desktopImageURL`, falling back to the solid color if it can't load) / solid color / nothing (transparent). `.trimShadow` returns the capture untouched. All rendering is in the capture's pixel space — padding is converted from points via the screen's backing scale by the caller.
- `Views/Annotation/AnnotationView.swift` — SwiftUI content hosted via `NSHostingView` in the annotation window: the markup canvas on a small material mat, and nothing else (the toolbar pill is its own window — see `MarkupToolbarPanel`). Takes the shared `MarkupCanvasController` as an `@ObservedObject` (`AnnotationCoordinator` owns it) and holds the window's zero-sized `keyboardShortcuts` (⌘S/⌘⇧S, ⌘Z/⌘⇧Z, ⌘+/⌘−/⌘0/⌘1), which is the only place they can live — the toolbar panel never becomes key.
- `Views/Annotation/MarkupToolbarPanel.swift` — borderless, non-activating `NSPanel` holding `MarkupToolbar`, added as a **child window** of the annotation window and pinned centered `Layout.toolbarGap` below its bottom edge. Also holds `AnnotatedFileDrag` and the flatten-then-export plumbing the output buttons need. Sizes itself to the pill (measured in SwiftUI via `.fixedSize()` + `onGeometryChange`), so no transparent margin swallows clicks; `reposition()` is the single placement path, called by the panel itself on a size change and by the coordinator on window resize.
- `Views/Annotation/MarkupCanvasView.swift` — `NSViewControllerRepresentable` hosting PaperKit's `PaperMarkupViewController` (the PencilKit-backed markup canvas) with the screenshot as its `contentView` background. Zoom is decoupled from the window: it opens at actual size and `zoomRange` spans 50 %…800 % of that, so you can zoom out past fit and the capture floats in empty canvas. Pinch/scroll zoom and pan happen natively inside the remote canvas; the toolbar's zoom controls and ⌘+/⌘−/⌘0/⌘1 go through `MarkupCanvasController.setZoom`. Its `Coordinator` now does almost nothing — see the zoom bullet under Non-obvious things for why the enforcement loop it used to run is gone.
- `Probe/OnboardingRenderProbe.swift` — renders each onboarding step to a PNG (see the onboarding bullet under Non-obvious things). `Probe/FreeZoomProbe.swift` / `Probe/UndoProbe.swift` / `Probe/ProbeCanvas.swift` — env-gated diagnostic harnesses for the annotation viewport and the undo history (see their bullets under Non-obvious things), plus the shared handle on the live canvas controller they both reach through. Inert in normal runs.
- `Views/Annotation/MarkupCanvasController.swift` — `ObservableObject` shared between toolbar and canvas: tool/color/width state applied as `PKTool`s, shape/line/text insertion via `PaperMarkup` mutation, crop (`applyCrop`), the undo/redo history (`undo`/`redo`/`canUndo`/`canRedo` — see the undo bullet under Non-obvious things), zoom (`setZoom`/`zoomIn`/`zoomOut`/`zoomToFit`/`zoomToActualSize`, expressed as a fraction of the capture's actual size), the published `visibleCanvasFrame` viewport (see the crop and zoom bullets under Non-obvious things), and async flatten-export (`PaperMarkup.draw` over the original `CGImage` at full pixel resolution). UI-layer only — never touches Services.
- `Views/Annotation/MarkupToolbar.swift` — bespoke SwiftUI pill. **Its contents and their order come entirely from `AppSettings.markupToolbarLayout`** (read live via `@AppStorage`, so open windows follow an edit): `mainControls` is a `ForEach` over the stored items and a `view(for:)` switch, with no grouping logic, because separators are items the user places rather than something the app infers. Upload is the one item that can be placed and still not appear — it needs a configured provider, or it would show and then fail. Undo, redo and the four zoom controls ship *unplaced*: their shortcuts (⌘Z / ⌘⇧Z, ⌘+ / ⌘− / ⌘0 / ⌘1) cover them for most people, and the pill is for what you reach for with the mouse — so they're opt-in from the tray for anyone who wants them visible (`ToolbarIconButton.isEnabled` dims them when the history is empty, since a custom button label doesn't dim itself under `.disabled`). The drag handle's payload is `AnnotatedFileDrag` (in `MarkupToolbarPanel.swift`): a `Transferable` whose `FileRepresentation` flattens the canvas and writes a temp PNG lazily, only when a drop destination requests the file — there is no file on disk before that. Clicking the insert button, the color swatch, or the stroke-width squiggle (`scribble.variable`, weight-mapped to the current width) slides the pill's controls out for a preset row (colors with the system `ColorPicker` as the last option; the five widths from `MarkupCanvasController.strokeWidthPresets`; or the shape/line/text icons). Picking a color or stroke slides the main controls back; the shape row deliberately stays open for repeat insertions (the armed shape is accent-highlighted, clicking it again disarms) and dismisses only via its ✕.
- `Views/Annotation/CropOverlay.swift` — the crop surface mounted over the canvas while `MarkupCanvasController.isCropActive`: drag to create the rect, 8 handles to resize, drag inside to move, dim outside (even-odd path fill), ✓/✕ confirm bar with live pixel dimensions, Return applies / Esc cancels. Same render-pixels-to-capture-input requirement as `ShapeInsertionOverlay`.
- `Views/Overlay/SelectionOverlayWindow.swift` / `SelectionOverlayView.swift` — the full-screen borderless overlay used for both Area (drag-to-select) and Window (hover-to-highlight) modes. One overlay window is created per `NSScreen` and shown simultaneously; only the screen the user interacts with produces a result, the rest are dismissed.
- `Views/Preview/ScreenshotPreviewPanel.swift` — borderless, non-activating, resizable floating panel (AppKit) with aspect-ratio-locked resize and drag-to-move.
- `Views/Preview/ScreenshotPreviewView.swift` — SwiftUI thumbnail hosted in the panel; reveals a row of circular action buttons (open in Finder, copy, edit-stub, drag-out-file) centered along the bottom on hover. When the capture wasn't saved to disk, Reveal in Finder is hidden and drag-out is backed by a temp PNG (`ScreenshotSaver.writeTemporaryPNG`, written by `ScreenshotPreviewController` at show time).
- `Views/Preview/HoverTrackingArea.swift` — `NSViewRepresentable` bridge providing hover detection that works while QuickSnap isn't the active app (see below).
- `Views/Settings/SettingsView.swift` — the `Settings` scene's root: `NavigationSplitView` sidebar (General/Markup/Hotkeys/Intelligence/Uploading/Advanced/About). Sized as a **range**, not a fixed frame — the Markup tab's toolbar editor lays items out in one row like the real pill, and pinning the window squeezed the rest of the page instead. The sidebar is pinned via `navigationSplitViewColumnWidth` so extra width goes to the detail pane. All sections are built; `PlaceholderSettingsSection` is now unused but kept for future tabs.
- `Views/Settings/AdvancedSettingsView.swift` — Advanced tab. Deliberately **not** a power-user feature bucket (see the note under Non-obvious things): permissions status/troubleshooting, upload timeout and retries, retention, Copy Diagnostics (redacted), and Reset All Settings.
- `Views/Settings/SliderWithValue.swift` — the shared numeric row (slider + formatted readout) used by General and Advanced.
- `Views/Settings/ImageOptionPicker.swift` — generic picker whose options are labelled thumbnails with an accent ring on the selection (currently the Window Screenshots background style). Reusing it for another setting is a set of imagesets plus an `Option` array — it has no drawing code to extend, which is the point. Tiles share the row width evenly, so all thumbnails must share `Layout.thumbnailAspectRatio` (120:84) or the row's heights won't match. `Layout` sits at file scope because a nested enum inside a generic type can't hold static stored properties.
- `Views/Settings/IntelligenceSettingsView.swift` — Intelligence tab: the on-device AI master toggle (`aiEnabled`) with live availability, the `{describe}` filename switch (which edits the *template* rather than storing a second flag — the template stays the single source of truth), the capture-index toggle with backfill progress and Rebuild, and `MCPSettingsSection`. It's the first UI the `AIProvider` seam has had; the seam deliberately shipped without one.
- `Views/Settings/MCPSettingsSection.swift` — the MCP server's sections *within* the Intelligence tab: toggle, port, live status from `MCPServerStatus`, and the copyable client config snippet (its real job — the server is useless until the client has the URL and token, and hand-assembling that from three fields is where the feature would get abandoned). It had its own "Integrations" tab until that read as a category with one member; it belongs with the rest of the agent-facing surface.
- `Views/Settings/UploadingSettingsView.swift` — Uploading tab: master toggle, provider picker, the selected provider's own section (`ImmichSettingsSection` / `S3SettingsSection`, private subviews in the same file), then the provider-neutral behaviour and button-visibility toggles. Each provider section builds credentials from the *typed* values rather than from `AppSettings`, so Test connection and album loading work before the settings are committed to a working state. Secrets go straight to the Keychain on change.
- `Views/Settings/MarkupSettingsView.swift` — Markup tab: default color (the toolbar's preset swatches + a hex-bridged `ColorPicker`), default stroke size as a *step index* into the per-image preset ladder (absolute pixels would read differently across capture sizes — the squiggle-weight buttons mirror the toolbar), the close-after-saving toggle, and `MarkupToolbarEditor`.
- `Views/Settings/MarkupToolbarEditor.swift` — drag-and-drop arrangement of the toolbar: a mock pill you drag items into, within and out of, over a tray of what's unplaced. The pill is a **mock rather than the live `MarkupToolbar`** on purpose — the real one's buttons want the same mouse-down a drag does, so a draggable copy would fight itself; both draw from `MarkupToolbarItem.symbolName`.
- `Services/MarkupToolbarLayout.swift` — the item enum and the stored order, with the migration from the five per-button visibility flags it replaced.
- `Views/Settings/HotkeysSettingsView.swift` — Hotkeys tab: one `HotkeyRecorderField` per action (click to record via a local `NSEvent` key monitor: Esc cancels, Delete clears, invalid combos beep; assigning a combo used by another action clears it there). `HotkeyShortcut(event:)` decides validity: printable key + at least one of ⌘⌥⌃, or a function/navigation key alone.
- `Views/Settings/GeneralSettingsView.swift` — General tab: save-folder row (`NSOpenPanel` Choose…, Reset back to default), the After screenshot Show/Copy/Save checkboxes, the Notifications section (a position picker and an auto-dismiss duration slider each for the preview panel and the toast — the preview's picker adds Dynamic, the toast's adds Notification; numeric rows share the `SliderWithValue` subview. Picking Notification requests notification authorization there and then, so the system prompt appears next to the switch that caused it instead of mid-capture behind an overlay, and shows an "Open System Settings" row if permission is missing; the toast's duration slider hides, since Notification Center owns its own timing), the Text Recognition toast-preview toggle, and the Window Screenshots section (background style as an `ImageOptionPicker` — the style→imageset mapping lives here, not on `WindowBackgroundStyle`, which is a Services type and stays UI-agnostic — padding slider, solid-color ColorPicker bridged to the stored hex string). Uses `@AppStorage` with `AppSettings.Keys`/`Defaults`.
- `Views/ToastView.swift` — the toast pill's SwiftUI content (icon + message on a material capsule); `ToastController` owns presentation and timing.
- `Views/Motion.swift` — house motion style (full rationale in `docs/motion-design.md`): `Motion.panelSpring`/`Motion.revealSpring` (critically damped springs), `Motion.reduceMotion` (AppKit-side Reduce Motion check for coordinators; SwiftUI views use `@Environment(\.accessibilityReduceMotion)` instead), and `PressScaleButtonStyle` (press-down scale feedback — use it instead of `.plain` on icon buttons).
- `Views/Annotation/ToolbarIconButton.swift` — circular icon button shared by `MarkupToolbar` and `CropOverlay`'s confirm bar: hover highlight, press-down scale, accent-tinted active state. New toolbar-style buttons go through this rather than hand-rolling the 28×28 circle.
- `Views/ContentView.swift` — leftover from the SwiftUI template, currently unused. Kept as a starting point if a Preferences/About window is added later.

## Non-obvious things

- **Immich has no client-selectable folder — the destination is an album.** `POST /api/assets` has no folder/path field, and Immich's Folders view (`GET /api/view/folder`) is *read-only*: it browses by `originalPath`, which the server assigns from its own admin-configured storage template. The only grouping the API exposes to clients is the album (`PUT /api/albums/{id}/assets`), which is why Settings → Uploading offers an album picker and not a folder chooser. Don't re-litigate this without re-reading the spec (`open-api/immich-openapi-specs.json` in the immich repo — pull it directly, secondhand docs are unreliable). Other verified details: the upload response's `status` is `created` **or** `duplicate` (checksum dedupe); `deviceAssetId`/`deviceId` are sent for old-server compatibility and are safe because Immich validates with non-strict Zod objects, which strip unknown keys rather than rejecting them. Full write-up in `docs/uploading.md`.
- **`Config/Info.plist` exists solely for App Transport Security** (`NSAllowsLocalNetworking`, so a LAN Immich or MinIO over plain `http://192.168.x.x:2283` isn't blocked; public hosts still require HTTPS). Two constraints on it: it lives *outside* `QuickSnap/` because that folder is a synchronized group and an `Info.plist` inside it would also be copied in as a bundle resource; and `GENERATE_INFOPLIST_FILE` stays `YES`, with Xcode merging the `INFOPLIST_KEY_*` build settings on top — so only keys that can't be expressed as a flat build setting belong in the file.
- **An `NSHostingView` in a plain `NSWindow` needs `sizingOptions = []`, or SwiftUI decides how big the window is.** By default the hosting view pushes the content's computed min/max size onto the window as `contentMinSize`/`contentMaxSize` — and it derives the minimum by laying the content out at its *narrowest*, where every `Text(…).fixedSize(horizontal: false, vertical: true)` wraps into a column and grows without bound. The onboarding window measured a minimum of **156 × 3380 pt** and opened taller than the display with its content off-screen, looking for all the world like a blank window. Clear `sizingOptions` and call `setContentSize(_:)` for any fixed-size window whose content is SwiftUI; the annotation window escapes it only because its content is a canvas with no wrapping text.
- **Onboarding is for what a first run breaks on, not a tour.** Three of its six screens exist because of specific failures: Screen Recording permission (without it nothing works, and macOS usually won't hand a fresh grant to a running process — the screen says so, because a user who grants access and still can't capture concludes the app is broken), the save folder (its first write blocks inside the syscall on a TCC prompt, so the step warms it off-main while a screen about saving is up), and the shortcuts (OCR and Copy for AI are reachable *only* by shortcut or menu, so a user who never sees them never learns they exist). The rest are preferences with a real split. Deliberately absent: anything destructive (retention), anything needing credentials (uploading), and anything you'd only understand after using the app. The window is a plain `NSWindow`, not the `Settings` scene — that scene can't be opened from AppKit at all (see the `showSettingsWindow:` note below).
- **`ImageRenderer` cannot draw AppKit-backed controls, and fails *loudly enough to look like a bug*.** `Probe/OnboardingRenderProbe.swift` (`QUICKSNAP_ONBOARDING_RENDER=<dir>`) renders the onboarding steps to PNGs so layout can be checked without a Screen Recording grant — a terminal-launched process has none, so `screencapture` just fails with "could not create image from display". But every `Toggle`, and every drag chip in `MarkupToolbarEditor`, comes out as a **yellow tile with a red prohibition sign**. That's the renderer's placeholder, not a broken control: the probe is good for spacing, typography, wrapping and overflow, and says nothing about anything AppKit draws.
- **Settings → Advanced is a support page, not a power-user bucket.** Anything a user would go looking for belongs on the page it relates to — filename templates and image format live in General beside the save folder, because burying them would hurt discoverability. Advanced holds only what is *diagnostic or destructive*: permission status, upload timeout/retries, retention, redacted diagnostics, and reset. Resist adding features there just because they feel advanced.
- **The MCP server is HTTP on loopback, not stdio — and that is not a shortcut.** An MCP client *launches* a stdio server as a child process, and QuickSnap is a menu-bar app that is already running, so there is nothing to launch. The alternative is a helper executable in the bundle forwarding over XPC, which buys only "no open socket" in exchange for a second binary and an IPC protocol. Because the socket is the trade, don't weaken what pays for it: loopback-bound via `requiredLocalEndpoint` (not just `NWListener(on:)`), off by default, Keychain-stored bearer token, `Origin` validated against DNS rebinding, and a toast on every capture the user didn't trigger.
- **Agent-initiated captures deliberately bypass the after-capture actions** — no save, no clipboard, no preview panel — and window captures skip `WindowBackgroundRenderer`. An agent asked for pixels; a presentation-styled shot is worse input, and writing a file plus stealing the clipboard on every tool call is noise nobody asked for. The tool result hands back a temp-file path instead, alongside a downscaled inline image (a retina full-screen PNG base64'd into JSON is tens of megabytes and would eat a model's context).
- **Testing the MCP server from a terminal hits two traps**, both cost real time: `defaults read/write com.dylanduff.QuickSnap` is redirected into a leftover sandbox container (`~/Library/Containers/com.dylanduff.QuickSnap/`) while the unsandboxed app reads `~/Library/Preferences/…`, so the two drift silently — address the plist by path and quit the app first, since a running instance flushes its cached domain over external writes. And a terminal-launched instance has **no Screen Recording permission** regardless of QuickSnap's own grant, because TCC attributes it to the responsible process (the terminal), so every capture tool returns the permission error. Details in `docs/mcp.md`.
- **The on-device model takes no image input.** `SystemLanguageModel`'s `respond` overloads accept only `Prompt`/`String` — no image or attachment parameter (verified against the SDK's `.swiftinterface`, which is ground truth here as it is for PaperKit). So every on-device task describes a capture *in text*: Vision's OCR plus the app/window it came from, which is why `CaptureDescriptionRequest` carries `recognizedText` rather than a `CGImage`. Anything that genuinely needs to see the picture needs a remote provider. Also: read `availability` fresh every time (it changes outside the app when Apple Intelligence is toggled or the model finishes downloading), and truncate OCR input — a full-screen transcript overflows the context window and fails the whole request.
- **`{describe}` resolves *after* the file is written, never before.** A capture that isn't on disk until a model answers is a capture that can be lost, and the round trip is seconds — so the file lands with the token empty and `CaptureCoordinator.describeAndRename` moves it once the description arrives. Three properties hold it together, each of which has already been a bug or was verified rather than assumed: `ResolvedFilename` keeps the name's *inputs* so the second render is identical (`{counter}` advances per call and `{random}` used to re-roll — the standalone test caught the rename landing on an unrelated name); the rename is a `moveItem`, which preserves the `FileTag` xattr (verified — **never** copy-then-delete, that orphans the file from retention); and `CaptureFile` is the box the preview and annotation window observe so their URLs follow. Every failure — AI off, provider unavailable, empty result, a slug that sanitizes to nothing — leaves the already-complete name alone.
- **There's still no AI provider picker** — there's one conformer. A second adds an enum, a picker, a Keychain-backed key and a branch in `AppSettings.aiProvider`, and nothing upstream changes.
- **Copy for AI's clipboard write is one item with two representations** (`ScreenshotSaver.copyToClipboard(_:text:)`): markdown as `.string`, PNG as `.png`, so a terminal takes the text and a chat window takes the picture. Two separate *items* wouldn't work — most readers only look at the first. Which representation a given app prefers can't be controlled, so an image-first paste target silently drops the context; the format is unverified against real chat tools. `copyToClipboard(_ image:)` was deliberately left alone (it writes an `NSImage`, offering AppKit's full representation set, which is the better write when there's no text to carry).
- **The search index is derived data, and every part of it is built to be thrown away.** `CaptureIndex` lives in Application Support, only ever holds files carrying the `FileTag` xattr (it reads the folder through `CaptureLibrary`), and self-heals: `search` drops and deletes rows whose file has disappeared, so a hit never opens nothing. There is deliberately **no "already backfilled" flag** — one was tried and the flag outlived the database it described, leaving search silently empty forever; the work list is a diff of the folder against the index instead, which costs one directory listing and one `SELECT` per launch and makes "user enabled indexing later" need no special case. Retention feeds it too: `SaveFolderCleaner.clean` returns the URLs it trashed rather than a count, and callers drop those rows.
- **Search-query text never reaches FTS5's query syntax.** `CaptureIndex.matchExpression` splits on anything that isn't a letter or digit, then quotes and prefix-matches each term — so a stray `"` can't be a syntax error and `NOT`/`NEAR` can't quietly change the search. Verified with the standalone test in `docs/search.md`.
- **The search panel is the only panel in the app that takes key status.** The preview and toast go out of their way not to (`canBecomeKey == false`, non-activating) so they never steal focus; a search box that can't be typed into is nothing, so this one overrides `canBecomeKey` and activates the app. No activation-policy switch is needed — an accessory app can be frontmost without gaining a Dock icon, unlike the annotation window which wants one. Its keyboard handling uses **zero-sized `Button`s with `keyboardShortcut`, not `onKeyPress`**: shortcuts resolve through `performKeyEquivalent`, which runs before the focused text field's editor sees the key, so ↑/↓ move the selection instead of the insertion point and ⌘↩ is never swallowed.
- **A held upload is not a failed upload.** The redaction gate runs *before* `beginUpload`, so a capture that gets held never shows the progress pill and never touches the reference count that keeps concurrent uploads reporting once. Two more traps, both hit while building it: the `proceed` continuation must take the **reviewed image** (the first version closed over the original capture, so redacting and continuing would have uploaded the unredacted pixels — precisely the failure the feature prevents), and the held-upload handler is passed **per call** rather than stored, or a second upload starting during the first one's OCR pass overwrites it and the review opens against the wrong capture.
- **Redaction boxes are the union of two estimates, deliberately.** Vision's per-substring box was exact for one of three measured fixtures and started ~500 px early on the other two; every observed error over-covered, but a box landing short leaves the tail of a key readable. `SensitiveContentDetector.redactionRect` unions Vision's box with a proportional estimate from character offsets. Re-run the end-to-end suite in `docs/redaction.md` — render text, detect, redact, **re-OCR the redacted image** — rather than eyeballing rectangles.
- **OCR mangles credentials, and the patterns are written for that.** Vision read `AKIAIOSFODNN7EXAMPLE` as `…DNNZEXAMPLE` (a `7` as `Z`) and the match still fired, because the character classes accept any `[A-Z0-9]` run after a known prefix. Don't tighten them to "correct" patterns — matching a slightly-wrong transcription of a real key is the point.
- **Window configuration from an `NSViewRepresentable` must not be a one-shot `DispatchQueue.main.async`.** `WindowConfigurator`'s original form hopped once, read `view.window`, and returned silently when it was nil — which happened often enough that the settings window's transparent title bar, `.resizable` style mask and order-front were sometimes never applied at all, and it looked like each of those features was individually broken. It now configures from `viewDidMoveToWindow` (AppKit's own "you're in a window now" callback), again on `didBecomeKey`, and on every SwiftUI update, all idempotent.
- **SwiftUI's `Settings` scene builds a non-resizable window**, whatever the content's frame says — the size *range* comes from the SwiftUI frame, but `.resizable` has to be inserted into the style mask by hand or the drag corners are inert.
- **`NSApp.sendAction(Selector(("showSettingsWindow:")))` returns `true` and does nothing** on macOS 26 — something in the responder chain claims it, but no window is created. There is no way to open the Settings scene programmatically from AppKit; `@Environment(\.openSettings)` is the only route, which also means a diagnostic that needs the settings window can't open it itself. Two probe rounds were spent measuring a window that never existed before this was established (2026-08).
- **The Settings… menu item is a `Button`, not a `SettingsLink`.** `SettingsLink` opens the window without activating the app, and QuickSnap is an accessory app that's rarely frontmost — so the window would open *behind* whatever the user was looking at, which reads as the menu item having done nothing. The button calls `NSApp.activate` and then `openSettings()`; `WindowConfigurator` also orders the window front on first creation, since that happens after the activation.
- **The markup toolbar is user-arranged, which changed two older rules.** Contents and order live in `MarkupToolbarLayout` (JSON in UserDefaults); an *absent* key means "never customised" and resolves to the default layout, while an empty array is a legitimate choice — so the two can't share a representation. Separators are placeable items, because once anything can sit anywhere there are no groups left for the app to infer. And the old "at least one export button stays on" interlock is gone: `AnnotationView.keyboardShortcuts` provides ⌘S / ⌘⇧S (and ⌘Z / ⌘⇧Z) regardless of the layout, which is what makes free removal safe. **Deliberately no ⌘C** — the canvas is a remote PaperKit view where ⌘C means "copy the selected text" while a text box is being edited, and a SwiftUI `keyboardShortcut` resolves through `performKeyEquivalent` *before* the remote view sees the key. ⌘Z is safe by the same reasoning run the other way: the remote implements no undo of its own (measured), so there's nothing there to shadow. The shortcuts live in the window's own content because the toolbar panel is `canBecomeKey == false` and never receives key events; the undo pair is `.disabled` when the history is empty, so the key isn't swallowed by a no-op.
- **Retention only ever deletes files QuickSnap tagged.** `FileTag` writes an extended attribute on every saved file and `SaveFolderCleaner` refuses to consider anything without it, never recurses, and uses the Trash rather than `removeItem`. The save folder is user-chosen and the app is unsandboxed, so this is the property that makes the feature acceptable at all. If the attribute is lost the file is kept — retention under-deletes by design.
- **A JPEG request silently stays PNG when the capture has alpha** (`ScreenshotSaver.effectiveFormat(for:)`), because a transparent window capture flattened onto black is never what someone wants. Relatedly, annotation drag-out is always PNG: `AnnotatedFileDrag` declares a *static* `exportedContentType`, so the file has to match what the drop destination was promised.
- **`ImageOptionPicker`'s thumbnails are generated, not hand-drawn or live.** `Tools/GenerateThumbnails.swift` (`swift Tools/GenerateThumbnails.swift` from the repo root) draws each option and writes the imagesets, light and dark variants, @1x and @2x. Two things follow: the PNGs are build output that happens to be committed, so edit the script and re-run rather than touching them; and the thumbnails are *illustrations* — the wallpaper tile isn't the user's wallpaper and the solid-colour tile isn't their configured colour (each appearance picks a fill the mock window reads against). Making them live previews would mean rendering in the view, which is the thing this design deliberately avoids.
- **Xcode project uses synchronized file groups** (`PBXFileSystemSynchronizedRootGroup`, Xcode 16+). Any `.swift` file placed anywhere under `QuickSnap/` (including new subfolders) is automatically part of the target — no `project.pbxproj` editing needed when adding or moving files. The flip side: a script that shouldn't be compiled must live outside `QuickSnap/` (hence `Tools/`), and the same hazard applies to stray resources — see the `Config/Info.plist` note above. Only build *settings* changes require touching the project file (use the `xcodeproj` Ruby gem, already installed, rather than hand-editing).
- **App Sandbox is disabled** (`ENABLE_APP_SANDBOX = NO`). This is required so the app can write directly to `~/Documents/QuickSnap` without a save panel on every capture. Consequence: this app cannot be Mac App Store-distributed as-is; that would require switching to user-selected-folder + security-scoped bookmarks.
- **`LSUIElement = YES`** hides the Dock icon (menu-bar-only app). There is no other window; `WindowGroup`/`ContentView` were removed from the app entry point.
- **Never do TCC-gated file I/O on the main thread.** The first access to a privacy-protected folder (~/Documents, ~/Desktop, ~/Downloads, ~/Pictures — sandbox off doesn't exempt us) blocks *inside the file syscall* until the user answers the system consent prompt. Doing that on the main thread mid-capture froze the app under its own full-screen overlay windows badly enough to require a machine restart (2026-07). Rules now in place: `ScreenshotSaver`/`AppSettings`/`WindowBackgroundRenderer` are `nonisolated` enums; saves and wallpaper reads run in `Task.detached`; and every capture entry point calls `prepareSaveFolderAccess()` (which touches the save folder off-main) *before* any overlay window is shown, so a first-run prompt appears while the app is responsive and nothing covers the screen. Keep all three properties for any new file-touching feature.
- **A hotkey for a switched-off feature is worse than no hotkey.** `RegisterEventHotKey` *consumes* the keystroke system-wide, so registering one for something that can't run silently swallows that combination in every other app. `HotkeyAction.isAvailable` gates this — `searchCaptures` is unavailable when capture indexing is off, which drops its registration, its menu bar item and its Hotkeys row together. The stored shortcut is never cleared, so turning the feature back on restores it, and `HotkeyCoordinator` re-applies on every UserDefaults change so both directions are immediate. Any future feature-gated action goes through the same property.
- **Global hotkeys use Carbon `RegisterEventHotKey`** — the one non-deprecated piece of Carbon and the only supported system-wide hotkey API (it's what all the hotkey libraries wrap). It needs no Accessibility/Input Monitoring permission and *consumes* the keystroke system-wide, which is also why the `.keyboardShortcut` hints on the MenuBarExtra items can never double-fire: SwiftUI never sees the event. The C event handler callback gets `self` back via an `Unmanaged` userData pointer and uses `MainActor.assumeIsolated` (Carbon delivers on the main event loop). F-keys/arrows can't be shown as SwiftUI menu hints (`KeyEquivalent` is character-only) — those shortcuts still work, they just show no hint in the menu.
- **Screen Recording permission**: checked/requested in `ScreenRecordingPermission` (`Services/ScreenCaptureManager.swift`). macOS frequently doesn't recognize a freshly-granted permission for an already-running process — the denial alert tells the user to relaunch QuickSnap after granting access in System Settings. This is expected, not a bug.
- **The preview's `anchor` is the third coordinate space in the capture path.** `CaptureCoordinator.finish` takes the captured region in *AppKit global* coordinates (bottom-left origin) — which neither source is already in, so both convert: an area rect comes from the flipped per-screen-local overlay space (`screenFrame(forOverlayRect:on:)`), and `SCWindow.frame` comes from global Quartz top-left space (`screenFrame(forQuartzRect:)`, flipped about `NSScreen.screens.first`, the display AppKit puts at (0, 0)). Window captures anchor on the window's own frame, not the styled image — background padding grows the capture symmetrically, so the center is the same either way.
- **Coordinate spaces**: `SelectionOverlayView` overrides `isFlipped = true` so its local view coordinates (top-left origin, points) match `SCStreamConfiguration.sourceRect`'s coordinate space directly — no manual flip needed when turning a drag rect into a capture request. Window-mode candidate frames (`SCWindow.frame`, which is in global Quartz top-left-origin coordinates) are converted to the same per-screen-local space by subtracting `CGDisplayBounds(displayID).origin` — see `startOverlaySession` in `CaptureCoordinator`.
- **Capture flow**: one `SelectionOverlayWindow` per connected `NSScreen` is created for every Area/Window session, all shown at once (so you can drag/click on whichever screen you're using); the rest are torn down as soon as one produces a result or the session is cancelled (Esc). The overlays are **non-activating `NSPanel`s** (`.nonactivatingPanel`, `hidesOnDeactivate = false`) so they can take key status for Esc without `NSApp.activate` — activating the app raised any open annotation/Settings windows above the app being captured and left them there (fixed 2026-07). Don't reintroduce an activate call on the capture path.
- **Preview panel** (`ScreenshotPreviewPanel`) uses `.nonactivatingPanel` + `canBecomeKey == false` so it can be dragged/resized/clicked without stealing focus/key-window status from whatever app is frontmost — same pattern as HUD/tooltip panels elsewhere in AppKit. It's also draggable (`isMovableByWindowBackground`) and resizable with `contentAspectRatio` locked to the screenshot's aspect ratio, like a video PIP window.
- **Hover detection must not use SwiftUI's `.onHover`** on the preview panel — that modifier tracks with `.activeInActiveApp`, which never fires while QuickSnap isn't the frontmost app (the normal case here, since the panel floats passively over whatever app the user was already using). `HoverTrackingArea` wraps a manual `NSTrackingArea` with `.activeAlways` instead. This applies to any future non-activating-panel UI, not just this one.
- **Cursor changes on the preview panel must not use `NSCursor.set()` in mouseEntered/mouseExited.** That approach sticks "until you or the window server changes it" per Apple's docs, and reliably goes stale after the user interacts with another app's window and comes back. `HoverTrackingArea` instead uses the `.cursorUpdate` tracking-area option + `cursorUpdate(with:)`, which AppKit itself re-invokes as needed and survives focus changes.
- **Window-background dragging/resizing bypasses `mouseDown`/`mouseUp` overrides on the window and its content views** — AppKit/the Window Server handles it before those reliably fire. `ScreenshotPreviewPanel` tracks mouse-down/up state via app-level `NSEvent` local monitors instead, and only considers a *drag* to have actually started once the frame visibly changes (`NSWindow.didMoveNotification`/`didResizeNotification`) while the mouse is still down — a plain click never moves the frame, so it doesn't trigger drag-only behavior (hiding the action bar, closed-hand cursor). Note those notifications fire synchronously from inside AppKit's tracking loop, so mutating SwiftUI `@Published` state directly from that callback doesn't animate — bounce through `DispatchQueue.main.async` first (still prompt; GCD main-queue dispatch is serviced during tracking loops, unlike a plain `Timer`).
- **The preview panel's auto-dismiss timer is hover-aware and interaction-permanent**: it pauses while hovered and restarts fresh on mouse-exit (so the dismiss fade can't start mid-way through the action bar's hide animation), and once the panel has actually been interacted with (`onInteractionBegan` — any mouseDown: click, drag-start, resize-start), auto-dismiss is disabled for that panel instance permanently. See `hasInteracted` in `ScreenshotPreviewController`.
- **No public API exists to opt an `NSWindow`/`NSPanel` out of macOS Sequoia's edge-drag window tiling/snapping.** Confirmed via an Apple Developer Forums thread ("Opt out of window tiling (macOS 15)") where a developer with the same problem got no working answer; Apple's own Sequoia AppKit guidance only covers tuning `minSize`/`resizeIncrements` for how tiling resizes your window, not whether it's eligible at all. `ScreenshotPreviewPanel.collectionBehavior` sets `.fullScreenDisallowsTiling`, which is a real, documented flag — but it only opts out of the older Split View full-screen tiling, not the newer edge-drag snap. If this becomes a real problem, the only other lever available is dropping `.resizable` from the style mask and reimplementing resize manually, which is unconfirmed to even help and hasn't been attempted.
- **Preview panel stays on the Space it was created on, and is not Mission-Control-draggable — this is an intentional trade-off, not an oversight.** `collectionBehavior` has no `.canJoinAllSpaces` (so it doesn't follow you to every Space) and no `.managed` (so it doesn't try to participate in Mission Control's per-Space tile view). Mission Control's "drag a window's tile to another desktop" gesture only works for `.normal`-level, Spaces-managed windows — `NSWindowCollectionBehavior.managed` is the *default* specifically for `NSNormalWindowLevel` windows. Our panel is deliberately `level = .floating` so it stays visible above whatever app is frontmost; a `.floating`-level window can't be made a draggable Mission Control tile without dropping to `.normal` level, which would let other apps' raised windows cover it and defeat the whole point of a persistent PIP overlay. Asked and confirmed with the user (2026-07) — keep `.floating`, don't revisit this trade-off without checking again.
- **Markup tools use PaperKit's canvas (`PaperMarkupViewController`) with a fully custom SwiftUI toolbar — Apple's `MarkupToolbarViewController` is deliberately not used.** Native macOS PencilKit has **no `PKCanvasView` and no `PKToolPicker`** (those are UIKit/Catalyst-only); it only ships the data model (`PKDrawing`, `PKInkingTool`, `PKEraserTool`, `PKLassoTool`) plus rendering. PaperKit is the macOS route to PencilKit drawing. The custom toolbar drives the canvas via `drawingTool: any PKTool` (settable), `indirectPointerTouchMode` (`.drawing` vs `.selection` — this is what decides whether mouse input draws or selects, so "Select" is a mode flip, not a tool), and shape/line/text insertion by mutating a copy of `markup` (`PaperMarkup.insertNewShape/insertNewLine/insertNewTextbox`) and assigning it back. Shapes and lines are drag-to-create: the toolbar's shape row arms `pendingInsertion`, `ShapeInsertionOverlay` captures the drag with a live preview (Esc or a bare click cancels), and the dragged geometry is inserted in canvas pixel coordinates (view points × zoom-to-fit scale; PaperKit's canvas is UIKit-based, so top-left origin matches SwiftUI directly). Only text still uses `suggestedFrameForInserting`.
  - An earlier PaperKit attempt was reverted: it hosted `PaperMarkupViewController` + `MarkupToolbarViewController` in a raw `NSViewController` set as `window.contentViewController` with Auto Layout, and fought window sizing continuously (several real constraint bugs, plus a never-root-caused narrow-window bug). The working approach hosts the canvas via **`NSViewControllerRepresentable` inside SwiftUI** — SwiftUI owns layout, no Auto Layout contact surface. Don't reintroduce the `contentViewController`/Auto Layout combination.
  - `PaperMarkupViewController` is `public` but **not `open`** — it can't be subclassed, so viewport work (applying `zoomRange`, placing the initial viewport) is done by observing `NSView.frameDidChangeNotification` on its view rather than overriding `viewDidLayout()`.
  - Ground-truth API for PaperKit/PencilKit (secondhand docs were incomplete/inconsistent) is the installed SDK's `.swiftinterface` files under `.../MacOSX.sdk/System/Library/Frameworks/{PaperKit,PencilKit}.framework/Versions/A/Modules/*.swiftmodule/` — read those directly. Key shape: background image goes in `PaperMarkupViewController.contentView` (not part of `PaperMarkup`); `FeatureSet.latest` covers all shape/text/drawing tools; `PaperMarkup.draw(in:frame:)` is the flatten/export API (macOS 26.0+).
  - Canvas coordinates equal the screenshot's **pixel** coordinates (markup bounds = image pixel size), so stroke widths/text sizes are in image pixels — `MarkupCanvasController` scales its width range with image size — and export composites at full resolution with no scaling.
  - **`PaperMarkup.draw(in:frame:)` does not flip for you.** Canvas coordinates are top-left origin (PaperKit is UIKit-based), but `draw` renders straight into the `CGContext`'s own bottom-left-origin space, so markup comes out mirrored about the image's horizontal centerline (text upside-down) unless the CTM is flipped first. `exportFlattened` draws the base image unflipped, then flips inside a `saveGState`/`restoreGState` pair for the markup pass. Verified with a standalone `swift` script rendering a known-position shape (2026-07) — the flip is *not* documented anywhere in the `.swiftinterface`.
- **Crop is a real, annotation-preserving crop, not an export-time mask.** `PaperMarkup.bounds` is settable and `transformContent(_:)` translates all existing markup, so `MarkupCanvasController.applyCrop` cuts the base image (`CGImage.cropping`, same top-left-origin pixel space as the canvas), shifts the markup by the crop origin, and shrinks `bounds` — prior annotations stay individually editable in place. `baseImage`/`canvasBounds` are `@Published`; `MarkupCanvasView` reacts in `updateNSViewController` by swapping the contentView image and its frame — and deliberately leaves the viewport alone, for a crop as much as for a redaction: fit is no longer where the canvas lives, so re-fitting would only yank the user out of wherever they were. The window doesn't move either, now that it isn't aspect-locked to the image. Crop *is* undoable, as one step covering the image, the bounds and the shifted markup together — they have to move as a unit, or restored annotations would land in the wrong coordinate space (see the undo bullet).
- **Zoom/pan state lives in `visibleCanvasFrame`** (`MarkupCanvasController`, image-pixel coordinates): pinch/scroll gestures are handled entirely inside the remote PaperKit process, so the *only* way the host app learns about them is `PaperMarkupViewController.Delegate.paperMarkupViewControllerDidChangeContentVisibleFrame` — the controller is that delegate and republishes `contentVisibleFrame` as a **pure observer** (it never corrects incoming reports; that lost, see below). Everything that maps view points → canvas pixels (`ShapeInsertionOverlay`, `CropOverlay`, `RedactionOverlay`) must go through `visibleCanvasFrame` (origin offset + uniform scale) — and that mapping has to keep working when the frame is *larger* than the canvas with a negative origin, which is what zooming out past fit looks like.
- **Zoom is independent of the window, and that is what killed the viewport enforcement.** The canvas opens at actual size (`MarkupCanvasController.defaultZoom`, one image pixel per *device* pixel — a 2× capture shows at half its pixel width, or it would open twice the size of the thing it's a picture of) and stays there; resizing the window reveals more or less of the canvas rather than rescaling it, Figma-style. `zoomRange` is `minZoom`…`maxZoom` (50 %…800 %) about actual size, with fit demoted from "the floor" to "where the Fit button goes". Facts behind it, all measured with `Probe/FreeZoomProbe.swift` (2026-08):
  - **The remote canvas holds absolute scale across a viewport resize by itself.** That was previously the *problem* — an entire verify-and-retry enforcement loop (`enforceViewport`), live-resize observers, and `lastRemoteReport` existed to convert it back into fit-tracking. Wanting the remote's own behaviour deleted all of it, along with every hazard it carried (the remote dropping host sets mid-drag and resuming at an unknowable moment, reports indistinguishable from gestures, sets silently clamped into no-ops).
  - **The canvas accepts a viewport larger than its content**, so zooming out past fit genuinely works: a requested `-800,-500,3200,2000` over a 1600×1000 canvas came back as `-801,-500,3203,2000`, image floating in empty space.
  - **It will not pan while zoomed out past fit.** With the content smaller than the viewport the remote re-centres it and drops the offset entirely (a pan request came back as the previous centred rect). Panning works normally when zoomed in. Nothing in the host can change this short of padding `PaperMarkup.bounds` out beyond the image, which would offset every coordinate space in the editor.
  - `zoomRange` accepts a lower bound below fit and reads back exactly, so the range really is the host's to set.
  - **Zoom commands are sprung by us, and stretch past a limit before settling** — `MarkupCanvasController.animateZoom`/`springViewport`, log-space interpolation, ~9 % overshoot when a request goes past the floor or ceiling. It's the one place the house no-overshoot rule is bent, because clamping made ⌘− at the floor do literally nothing (`docs/motion-design.md`). Pinch/scroll zoom is the remote's own and gets none of this.
  - **The opening viewport still needs verify-and-retry, and that is the one survivor of the enforcement machinery** (`MarkupCanvasView.Coordinator.placeInitialViewport`). A one-shot set at first layout fails two ways, both measured across repeated probe runs: it lands at a transient hosting-view size the window then grows out of (and the remote holds *that* scale), or it is dropped entirely before the remote is ready, leaving the canvas at the remote's own default of 1 point per image pixel — a window opening at 200 % on a retina capture, intermittently, run to run. So placement re-sends until `lastRemoteReport` matches the rect it asked for (never `visibleCanvasFrame`, a local assumption that would "converge" instantly), and cancels the moment the user grabs a window edge or touches a zoom control. If you make opening zoom a one-shot again, it will look fine roughly half the time.
- **Undo/redo is entirely ours — PaperKit has no undo API and the remote canvas implements none.** The `.swiftinterface` has no undo surface at all, and a synthesized ⌘Z over a freshly drawn stroke changed nothing (probe, 2026-08), so there was neither an API to call nor built-in behaviour to shadow. `MarkupCanvasController` keeps a stack of `CanvasSnapshot`s (markup value + base image + canvas bounds), and undo is "put the old value back". Five facts hold it together, each measured with `Probe/UndoProbe.swift` rather than assumed:
  - **`PaperMarkup` equality does not survive the remote round trip.** A restored value comes back structurally correct but `!=` its source, and its serialized size differs (244 → 603 bytes for the same empty markup). Never diff states to detect a change — use `contentsRenderFrame` for measurement and the delegate for change detection.
  - **`paperMarkupViewControllerDidChangeMarkup` fires exactly once per user stroke**, which is why there's no coalescing: one report is one undo step.
  - **A host-side `markup` assignment re-enters that same delegate, once.** `isApplyingSnapshot` suppresses the echo, cleared on the next main-queue turn because the report can arrive during the assignment or just after it. Without it every insertion and crop would record twice.
  - **The canvas reports a change when it first attaches**, before any edit — that left Undo enabled on an untouched capture. A report with no drawn content on either side of it is dropped (erasing the last markup still has content in the *previous* snapshot, so it records normally).
  - **A restored snapshot stays editable** — drawing after an undo works and records normally, so undo doesn't strand the canvas.

  Two deliberate carve-outs: crop is one step covering image + bounds + markup together (restoring markup laid out for a cropped image over the uncropped one would misplace every annotation), and **redaction clears the history outright** — every snapshot behind it holds the unredacted image, so an undo would put the credential back on screen. Insertions are now undoable, which they weren't before this existed.
- **Free-zoom probe** (`Probe/FreeZoomProbe.swift`; run `QUICKSNAP_FREEZOOM_PROBE=1 <DerivedData>/…/QuickSnap.app/Contents/MacOS/QuickSnap` from a terminal): opens an annotation window with a synthetic capture, checks it opens at 100 %, drives **real live-resize drags via CGEvents** (needs Accessibility for QuickSnap — it checks `AXIsProcessTrusted`) and asserts zoom is unchanged by them, then walks the zoom floor, ceiling, fit and actual-size paths and confirms a crop no longer moves the window. Prints PASS/FAIL per scenario, then terminates; inert without the env var. It replaced `ZoomResizeProbe`, which verified the fit-tracking behaviour that no longer exists. Re-run it after touching anything in the viewport path, and extend its scenarios rather than theorizing about remote-canvas timing.
- **Undo probe** (`Probe/UndoProbe.swift`; run `QUICKSNAP_UNDO_PROBE=1 <DerivedData>/…/QuickSnap.app/Contents/MacOS/QuickSnap`): same shape as the zoom probe — synthetic capture, real CGEvent strokes, PASS/FAIL per scenario. It draws, undoes via a posted ⌘Z (the real key-equivalent path, not a direct call), redoes, walks the history to empty, crops and undoes the crop, and checks a redaction wipes the history. `MarkupCanvasController` calls `UndoProbe.noteMarkupChanged()` from the change delegate so reports can be counted. Re-run after touching the history or any markup mutation.
- **The PaperKit canvas is an ExtensionKit REMOTE view** (`_EXHostView`/`NSRemoteView`; the actual canvas UI runs in `PaperKitExtension.appex`, a Catalyst process). Three non-negotiable consequences, all confirmed empirically (2026-07):
  - **Input routing over the canvas is decided by whether a layer above it actually RENDERS PIXELS, not by SwiftUI hit-testing** (confirmed empirically 2026-07, both directions). A `.overlay` that draws anything — even a 1 px decorative stroke with `.allowsHitTesting(false)` — silently kills ALL canvas mouse input (no drawing, no selection, no cursor changes; rendering and programmatic markup keep working): the window server sees the remote surface as occluded and stops routing input to the extension process, and SwiftUI's hit-testing opt-out doesn't exist at that level. Conversely, a **non-drawing** overlay (`Color.clear` + `contentShape` + gesture) does nothing at all: input keeps flowing straight to the extension process, bypassing the host app's responder chain, so the local gesture never fires either. Consequences: decorations must go in `.background` (the hairline border in `AnnotationView` is drawn behind, outset by 1 px) — `clipShape`, `aspectRatio`, `padding`, material backgrounds, and VStack siblings are all safe; and any overlay that *wants* to capture input (like `ShapeInsertionOverlay`, mounted only while a shape/line insertion is armed) must render something visible — it uses a 15% black dim, which both flips the input routing to the host app and signals the mode to the user.
  - **In-process synthetic events (`window.sendEvent`) never reach the canvas** — to exercise it programmatically, post real `CGEvent`s (`.cghidEventTap`); verify event delivery first with a control test (e.g. drag the title bar and check the window moved), since CGEvent posting silently no-ops without Accessibility permission. (A temporary env-gated probe using this technique — open an annotation window with a synthetic image at launch, CGEvent-drag the canvas, compare `markup` before/after — was how this class of bug was reproduced and verified; rebuild it if canvas input ever regresses.)
  - The background `NSImageView` set as `contentView` overrides `hitTest` → `nil` (`HitTestTransparentImageView`) — PaperKit's contentView pattern assumes iOS's non-interactive-by-default `UIImageView`.
- **Swift 6.2 upcoming-features gotchas** (this target enables `InferIsolatedConformances`, `MemberImportVisibility`, default-isolation `MainActor`): a `@MainActor` class's `ObservableObject` conformance is inferred *isolated* and then fails `@StateObject`'s generic constraint with a misleading "does not conform to protocol" error — declare it `final class Foo: nonisolated ObservableObject`. And `@Published` needs an explicit `import Combine` (SwiftUI's re-export isn't enough under `MemberImportVisibility`).
- **Annotation windows are standard, titled `NSWindow`s** (`styleMask = [.titled, .closable, .resizable, .miniaturizable]`) — native title bar, native traffic-light close button, native resize. A fully custom borderless window (own pseudo title-bar pill, own drag-to-move via a SwiftUI `DragGesture`, own close button, a `canBecomeKey` override since borderless windows default that to `false`) was tried first and reverted after repeatedly fighting us: the custom drag handler was jittery (SwiftUI's `DragGesture` `.global` coordinate space is relative to the window itself, so translation deltas fed back into moving that same window create a feedback loop — screen-space deltas from `NSEvent.mouseLocation` are what's actually needed for this kind of "drag this view to move its own window" logic), and a resize-related layout bug was never root-caused. Letting AppKit's native window chrome handle title bar/close/resize/drag removed that whole class of bug at once; only the markup tools pill remains bespoke SwiftUI. Multiple annotation windows can be open at once; `AnnotationCoordinator` is not a singleton-panel controller like `ScreenshotPreviewController`.
- **The annotation window's title bar blends into the content via `.fullSizeContentView` + `titlebarAppearsTransparent`** — but `.fullSizeContentView` alone is not enough with an `NSHostingView` content view: the hosting view still reports a safe-area inset for the title-bar region to its SwiftUI content, so content stops short of the top. The working recipe is `hostingView.safeAreaRegions = []` (set **after** attaching the hosting view to the window — safe-area computation is derived from the window context and setting it beforehand didn't fully take effect) plus `.ignoresSafeArea(.container, edges: .top)` in the SwiftUI root. The mat's top padding (`AnnotationView.Layout.matTopPadding`) is what keeps the canvas clear of the traffic lights. An earlier attempt without the safe-area fix broke sizing badly and was reverted.
- **The markup toolbar is a child window, not part of the annotation window's content.** It started as a row in the window's own `VStack`, which pushed the window's bottom edge (and therefore its native resize handles) a toolbar-height below the image, leaving the bottom corners in empty space either side of the pill — the corner handles were nowhere near the image they resize. AppKit has no way to restrict a window's resize region to a sub-rect, so the only fix is to get the toolbar out of the content rect: `MarkupToolbarPanel` is added with `addChildWindow(_:ordered:.above)`, which makes it follow the parent's moves, ordering, and miniaturization for free. Only resizes need it re-pinned (`windowDidResize` → `reposition()`), because AppKit tracks a child's offset from the parent's *old* frame origin. Consequences to keep in mind: the pill is `canBecomeKey == false` so clicking a tool doesn't pull key status off the window; its width tracks the pill's measured size frame-by-frame so it follows SwiftUI's own row-swap animation rather than running one of its own (see the sizing rules below); and dragging the window far enough down can push the pill off the bottom of the screen (it isn't clamped — the same thing happened before, just 64pt later).
  - **The panel spans the window's width with the pill centered in it — don't "fix" it to hug the pill.** The pill's width animates on every preset-row swap, and a window cannot resize in lockstep with the SwiftUI content inside it: `onGeometryChange` reports a size SwiftUI has *already* laid out and drawn at, so a panel tracking the pill is permanently a beat behind. Sizing it to the pill was tried and produced, in order: the capsule's ends clipped square while growing (read as the toolbar losing its corner radius), then — once slack was added to cover that — the pill sliding left or right as the panel's edges moved under already-drawn content. Growth slack, trailing-only slack, and leading alignment each fixed one direction and broke another; none of it addressed the cause. A fixed width does: the window doesn't change during a transition at all, so the width morph animates purely inside SwiftUI exactly as it did when the pill was a row in the window's own content. `pillSize` survives only to set the panel's height and to widen it past a window too narrow to fit the pill. The cost is transparent panel either side of the pill, which is the same footprint the annotation window itself occupied there before the split.
- **The annotation window resizes freely — the aspect-ratio lock is gone, deliberately.** It used to be constrained in the window delegate to "canvas at the image's aspect ratio + a fixed chrome offset" (`NSWindow.contentAspectRatio` can't express the constant offset), so the mat always framed the capture tightly. That only made sense while the canvas was a *frame* around the image; now it's a viewport onto a canvas the image floats in, so `windowWillResize` and `windowWillUseStandardFrame` are both gone and AppKit's own resize and zoom-button behaviour is exactly right. Two things went with them and don't need reintroducing: the least-squares projection that stopped corner drags juddering (there is no constraint left to resolve), and the post-crop window animation — cropping now changes what's on the canvas without touching the window at all. `AnnotationView.Layout.chromeSize` survives, but only to size a *new* window (capture at actual size + chrome, capped at 70 % of the screen).

## Conventions

- Saved filenames come from the user's template (`FilenameTemplate`), defaulting to `QuickSnap yyyy-MM-dd at HH.mm.ss` plus the configured format's extension, in the configured save folder (default `~/Documents/QuickSnap`).
- After a capture, up to three actions run per the General settings toggles (all on by default): save to disk, copy to clipboard, show the bottom-right preview panel.
- No capture sound (deliberately not implemented — revisit if wanted).
- Motion: critically damped springs by default via `Motion` constants (no overshoot unless a gesture carried momentum); enter/exit mirror the same path; every slide/scale degrades to a cross-fade under Reduce Motion; gesture-tracked geometry (crop rect, area selection) is never animated. Details in `docs/motion-design.md`.

## Build

```
xcodebuild -project QuickSnap.xcodeproj -scheme QuickSnap -configuration Debug build
```

Or open `QuickSnap.xcodeproj` in Xcode and run the `QuickSnap` scheme. Deployment target is macOS 26.5 (uses `SCScreenshotManager`, available since macOS 14).
